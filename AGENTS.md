# AGENTS.md — правила работы агентов в проекте

Проект использует OpenSpec: главные спеки — `openspec/specs/`, активные изменения — `openspec/changes/`.
Авторитетный источник правил и контекста проекта — `openspec/config.yaml` (поля `context` и `rules`);
при расхождении приоритет у него. Перед созданием или правкой артефактов изменения прочитать их.

## Рабочий цикл OpenSpec

- Обсуждение и анализ — `/opsx:explore`; новое изменение — `/opsx:propose`;
  реализация задач — `/opsx:apply`; правка артефактов — `/opsx:update`;
  перенос дельт в главные спеки — `/opsx:sync`; архивирование — `/opsx:archive`.
- CLI: `openspec` (`openspec --help`; статус, валидация и инструкции по изменению).

## Ключевые правила

- Артефакты, комментарии, Javadoc, сообщения пользователю и README — на русском языке;
  идентификаторы в коде и ключи настроек — на английском.
- Каждый Java-файл начинается с `// SPDX-License-Identifier: Apache-2.0`.
- Платформы Linux, macOS, Windows: любое решение с путями, файловой системой или
  блокировками учитывает все три.
- Данные пользователя в SQLite нельзя терять и портить; изменения хранения и миграций
  описывают поведение при сбое.

## Обязательные проверки до завершения задачи

- `./gradlew check` (spotless, errorprone с NullAway, spotbugs, тесты, покрытие строк
  не ниже порога из `gradle.properties`).
- Для логики БД и настроек — дополнительно `pitest`.
- Код в `src/verified` проверяется `openjmlProve`; контракты JML меняются только
  вместе с доказательством.
- Тесты UI запускать с `-Pheadless=true`.

## Проверка безопасности после правок Java-кода

После завершения любой задачи, в которой менялся Java-код — неважно, правил
ли ты сам или это сделал субагент (fixer, designer и т.п.) — до сдачи результата
прогоняй субагента `security-auditor` по изменённым файлам или диффу. Особенно
это касается кода, который затрагивает пользовательский ввод, секреты, запросы
к БД, REST-эндпоинты и внешние вызовы.

Если находки есть — перечисли их в итоговом ответе и предложи, как исправить.

Мелкие правки (форматирование, комментарии, doc-комментарии, переименования
без изменения логики) можно не прогонять, но тогда явно скажи, что проверка
безопасности пропущена.
