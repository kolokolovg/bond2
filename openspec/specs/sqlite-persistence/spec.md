# sqlite-persistence Specification

## Purpose
Определяет поведение локального хранилища на SQLite: инициализацию и миграции схемы и атомарность операций при параллельной работе нескольких потоков.

## Requirements

### Requirement: Инициализация и миграции схемы
Система SHALL разделять операции над БД: создание новой БД, открытие существующей и миграция существующей. Файл БД SHALL определяться путём из настроек (по умолчанию — из `DataDirectory`). При создании недостающие каталоги пути SHALL создаваться, а ещё не применённые миграции — применяться строго по порядку версий. Первый запуск с путём по умолчанию, когда файла нет, SHALL создавать БД автоматически.

#### Scenario: Первый запуск
- **WHEN** файла БД по пути по умолчанию не существует
- **THEN** файл создаётся и применяются все миграции, версия схемы становится актуальной

#### Scenario: Повторный запуск
- **WHEN** БД уже содержит актуальную версию схемы
- **THEN** миграции не применяются повторно, данные не изменяются

#### Scenario: Сбой миграции
- **WHEN** миграция завершается ошибкой
- **THEN** операция завершается ошибкой, частично применённые изменения этой миграции откатываются

#### Scenario: Пользовательский путь
- **WHEN** создаётся новая БД по пути в ещё не существующем каталоге
- **THEN** каталог и файл создаются, применяются все миграции набора

### Requirement: Атомарность единицы работы
Система SHALL выполнять группу операций с БД как единую транзакцию: либо все изменения фиксируются, либо ни одно.

#### Scenario: Успешная транзакция
- **WHEN** единица работы завершается без ошибки
- **THEN** все её изменения сохранены и видны последующим операциям

#### Scenario: Ошибка внутри транзакции
- **WHEN** в ходе единицы работы возникает исключение
- **THEN** все изменения этой единицы откатываются, исключение передаётся вызывающему

### Requirement: Корректность при параллельной работе
Система SHALL корректно обрабатывать одновременные транзакции из нескольких потоков: изменения не теряются, промежуточные состояния чужих незавершённых транзакций не видны, кратковременные блокировки БД не приводят к ошибке.

#### Scenario: Параллельные конкурирующие записи
- **WHEN** несколько потоков одновременно инкрементируют одно и то же значение в БД, каждый в своей транзакции
- **THEN** итоговое значение равно числу успешно завершённых инкрементов (без потерянных обновлений)

#### Scenario: Чтение во время записи
- **WHEN** один поток выполняет незавершённую транзакцию записи, а другой читает
- **THEN** читающий видит только зафиксированные данные и не блокируется надолго

#### Scenario: Кратковременная занятость БД
- **WHEN** запись ожидает освобождения блокировки БД в пределах настроенного таймаута
- **THEN** операция дожидается и завершается успешно, а не падает сразу с ошибкой занятости

#### Scenario: Превышение времени ожидания
- **WHEN** блокировка не освобождается за настроенный таймаут
- **THEN** операция завершается явной ошибкой, транзакция откатывается

### Requirement: Создание новой БД
Система SHALL создавать новую БД по указанному пути с применением всех миграций набора. Если файл по этому пути уже существует, создание SHALL завершаться ошибкой без изменения файла.

#### Scenario: Новая БД
- **WHEN** запрошено создание БД по несуществующему пути
- **THEN** создана БД с актуальной версией схемы

#### Scenario: Файл уже существует
- **WHEN** запрошено создание БД по пути существующего файла
- **THEN** выбрасывается ошибка, файл не изменён

### Requirement: Обнаружение устаревшей схемы
При открытии существующей БД система SHALL определять, есть ли неприменённые миграции, и сообщать об этом вызывающему, НЕ применяя их автоматически. БД с версией схемы новее известной приложению SHALL отклоняться с явной ошибкой.

#### Scenario: Схема устарела
- **WHEN** открывается БД, в которой применены не все миграции набора
- **THEN** результат указывает на необходимость миграции, содержимое файла не изменено

#### Scenario: Схема актуальна
- **WHEN** открывается БД с актуальной схемой
- **THEN** БД открывается без миграции

#### Scenario: Схема новее приложения
- **WHEN** в БД применены миграции, неизвестные приложению
- **THEN** открытие завершается ошибкой, файл не изменён

### Requirement: Резервная копия и откат при миграции существующей БД
Перед миграцией существующей БД система SHALL создать резервную копию файла (включая связанные WAL-данные, приведённые к согласованному состоянию) рядом с исходным файлом и проверить её целостность. Имя копии содержит метку времени; если такая копия уже существует, система SHALL выбрать свободное имя с числовым суффиксом, не перезаписывая существующую. Если миграция завершилась ошибкой, система SHALL восстановить БД из резервной копии и передать вызывающему ошибку миграции с исходной причиной; прежние копии при этом SHALL NOT удаляться. После успешной миграции система SHALL сохранять три последние резервные копии этого файла БД (включая новую) и удалять более старые.

#### Scenario: Успешная миграция
- **WHEN** миграция существующей БД завершена успешно
- **THEN** схема актуальна, резервная копия предыдущего состояния сохранена

#### Scenario: Неудачная миграция
- **WHEN** миграция существующей БД завершилась ошибкой
- **THEN** файл БД восстановлен из резервной копии и совпадает с состоянием до миграции, вызывающему передана ошибка миграции, прежние копии не удалены

#### Scenario: Сбой в середине набора миграций
- **WHEN** часть миграций набора применена, а следующая завершилась ошибкой
- **THEN** БД восстановлена к состоянию до начала всей миграции, ни одна из ранее применённых в этом запуске миграций не сохраняется

#### Scenario: Копия не прошла проверку целостности
- **WHEN** проверка целостности резервной копии не вернула «ok»
- **THEN** миграция не выполняется, БД не изменяется, возвращается ошибка

#### Scenario: Не удалось создать копию
- **WHEN** резервную копию создать не удалось
- **THEN** миграция не выполняется, БД не изменяется, возвращается ошибка

#### Scenario: Копия с той же меткой времени уже есть
- **WHEN** копия с такой меткой времени уже существует
- **THEN** новая копия создаётся с числовым суффиксом, существующая не изменяется, миграция выполняется

#### Scenario: Ограничение числа копий
- **WHEN** после успешной миграции у файла БД больше трёх резервных копий
- **THEN** остаются три самые новые, остальные удалены; копии других файлов и посторонние файлы не затрагиваются

### Requirement: Закрытие БД
Система SHALL предоставлять закрытие БД: оно SHALL дождаться завершения активных транзакций, привести файл БД в самодостаточное состояние (WAL-данные перенесены в основной файл), после чего новые транзакции SHALL отклоняться явной ошибкой.

#### Scenario: Закрытие с активной транзакцией
- **WHEN** БД закрывается во время выполнения транзакции
- **THEN** закрытие ждёт её завершения, изменения транзакции зафиксированы

#### Scenario: Использование после закрытия
- **WHEN** после закрытия запрашивается новая транзакция
- **THEN** операция завершается явной ошибкой

#### Scenario: Самодостаточный файл
- **WHEN** БД закрыта
- **THEN** рядом с файлом БД нет непустого `-wal` файла

### Requirement: Распознавание пустого и чужого файла
При открытии существующего файла система SHALL отличать пустой файл (0 байт) и файл SQLite без истории миграций приложения от БД приложения. Пустой файл SHALL инициализироваться актуальной схемой как новая БД, без предложения миграции. Файл SQLite, содержащий таблицы, но не имеющий истории миграций приложения, SHALL отклоняться ошибкой «не база данных приложения»; файл при этом SHALL NOT изменяться и миграция SHALL NOT предлагаться. Файл, не являющийся SQLite, отклоняется ошибкой чтения схемы, как и ранее.

#### Scenario: Пустой файл
- **WHEN** открывается существующий файл размером 0 байт
- **THEN** он инициализируется актуальной схемой, БД открывается без вопроса о миграции

#### Scenario: Чужая база SQLite
- **WHEN** открывается SQLite-файл с таблицами, но без истории миграций приложения
- **THEN** открытие завершается ошибкой «не база данных приложения», файл не изменён, миграция не предлагается

#### Scenario: Пустая база SQLite без таблиц
- **WHEN** открывается корректный SQLite-файл без таблиц
- **THEN** он обрабатывается как пустой: инициализируется актуальной схемой

#### Scenario: База приложения
- **WHEN** открывается БД с историей миграций приложения
- **THEN** поведение прежнее: актуальная схема открывается, устаревшая требует миграции, новее приложения отклоняется
