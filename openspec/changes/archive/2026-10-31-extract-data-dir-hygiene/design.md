# Design

## Context

Дублирование живёт в двух пакетах, каждый из которых зависит только от JDK: `settings/SettingsStore` (очистка `settings-*.tmp` при чтении, имя `settings.properties.bad-<штамп>` при восстановлении) и `persistence/BackupManager` (очистка `<имя-БД>.*.restore` перед миграцией, имя `<имя-БД>.bak-<штамп>` у копии). Оба поведения специфицированы (`app-settings` «Надёжная запись настроек», «Восстановление испорченного файла настроек»; `sqlite-persistence` «Очистка временных файлов отката», «Имена и хранение резервных копий») и обоими классами реализованы через `Clock`-параметр. Изменение стоит в зоне данных: поведение при сбое описано ниже для каждой точки.

## Goals / Non-Goals

**Goals:**

- Одна реализация «очистки осиротевших производных файлов» и «резервирования имени со штампом», устойчивая к гонке.
- Пакет `settings` остаётся независимым от `persistence` (зависимость удалена change'ом `cleanup-dead-code` и не возвращается).
- Все четыре специфицированных поведения сохраняются дословно; существующие тесты сценариев проходят без правки утверждений.

**Non-Goals:**

- Политика хранения копий (`BACKUPS_KEPT`, `pruneBackups`), откат миграции, `resetToEmpty` — не меняются.
- Перенос форматов имён дальше общего паттерна штампа (префиксы `.bad-`/`.bak-` остаются за вызывающими).

## Decisions

### 1. Нейтральный листовой пакет `files`, а не `persistence`

Компонент — публичный класс `StampedFiles` в новом пакете `ru.onlychill.bonds2.files`: на него ссылаются оба пакета, он сам — только на JDK. Граф остаётся ациклическим без связей между доменными пакетами.

- Альтернатива: положить в `persistence` рядом с `DataDirectory` — отвергнута: создавала бы зависимость `settings → persistence`, только что устранённую.
- Альтернатива: продублировать компонент в двух пакетах — отвергнута: возвращает исходную проблему.

### 2. Резервирование имени — атомарным созданием (единый вариант)

`reserve(anchor, base)` создаёт пустой файл `createFile'ом`; занято (`FileAlreadyExistsException`) — суффиксы `-1`, `-2`…; прочий `IOException` уходит вызывающему. `BackupManager` сохраняет сегодняшнюю механику. `SettingsStore.recover` резервирует имя bad-копии и заполняет его `Files.copy(..., REPLACE_EXISTING)` — замена собственного пустого файла, а не чужого.

- Альтернатива: сохранить два варианта цикла (exists-проба и createFile) как два метода — отвергнута: расходящаяся устойчивость к гонке и есть дефект; оба требования («не перезаписывая существующую») выполняются только атомарным вариантом строго.
- Поведение при сбое (bad-копия): сбой копирования после резервирования — удалить зарезервированный пустой файл (иначе «пустая копия» выглядит как созданная), затем WARNING и `LoadResult(defaults, null, true)`, как сегодня. Сбой резервирования — WARNING без копии, как сегодня.

### 3. Очистка — один метод с журналированием

`sweepOrphans(dir, glob, what)`: отсутствующий каталог — no-op; DirectoryStream по glob; обычные файлы удаляются `deleteIfExists`; не-файл и сбои удаления/просмотра — WARNING с описанием `what`, выполнение вызывающего не прерывается. Унификация на диагностируемый вариант: не-файл журналируется и в случае настроек (сегодня — молчаливый пропуск); изменение касается только журнала.

- Альтернатива: параметр «журлировать не-файл или молчать» — отвергнута: два режима одной операции без требования, различающего их, — ложная конфигурируемость.

### 4. Штамп — общий паттерн, база имён — за вызывающими

`stamp(Clock)` возвращает `yyyyMMdd-HHmmss`; константы `BAD_STAMP` и `BACKUP_STAMP` удаляются. Префиксы `.bad-`/`.bak-` и позиция суффикса остаются у вызывающих — это части их специфицированных имён.

- Альтернатива: компонент строит полное имя — отвергнута: компоненту незачем знать имена чужих доменов.

### 5. Исключения компонента — только JDK

Компонент бросает `IOException` и не знает `PersistenceException`/`UncheckedIOException`: обёртки остаются за вызывающими (миграция — `MigrationException`, настройки — WARNING-ветка `recover`). Тексты журналов очистки становятся общими с `what` вместо двух близких формулировок.

- Альтернатива: компонент с собственным типом ошибки — отвергнута: дополнительный тип без новой семантики.

## Risks / Trade-offs

- [Микроокно «зарезервированный пустой файл» у bad-копии до копирования] — при падении процесса в этом окне остаётся пустой `.bad-`-файл; сегодня остался бы частичный. Спека состояние в этом окне не описывает, параллельных писателей нет (блокировка экземпляра); свернувшийся случай убирается вручную так же, как частичный сегодня.
- [Смена формулировок журналов очистки] — grep-и по старым текстам в тестах отсутствуют (проверено); журналы не являются контрактом.
- [pitest: перестановка цикла суффиксов] — новые тесты компонента покрывают каждую ветку (занято, свободно, не-файл, сбой удаления, сбой просмотра); существующие сценарные тесты — интеграционную склейку.
- [Платформы] — `createFile`, `deleteIfExists`, `DirectoryStream` одинаковы на Linux/macOS/Windows; имена строятся через `resolveSibling`/суффикс без разделителей путей; скрытый префикс `.bak-` не меняется.

## Migration Plan

Одно изменение, обычная сборка (`./gradlew check -Pheadless=true`, затем `pitest`). Форматы и имена файлов не меняются; откат — revert целиком (файлы, созданные в новом коде, именуются идентично старому).
