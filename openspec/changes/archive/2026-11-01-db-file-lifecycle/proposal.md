# Proposal

## Why

У приложения одна база данных, однако текущий жизненный цикл файла БД построен
вокруг выбора пути: три источника истины (сохранённый путь, путь по умолчанию,
флаг автооткрытия), отдельная операция создания с правилами неперезаписи,
асимметрия поведения «файла нет» для разных путей и тяжёлая механика отката
миграций через восстановление из поколений резервных копий. Большая часть
сложности спек `main-window`, `sqlite-persistence` и `app-settings` существует
только для обслуживания этого выбора. Пользователь принял решение: выбор пути
избыточен, упрощение поведения приоритетнее текущих спецификаций.

## What Changes

- **BREAKING**: единственная БД приложения — всегда файл в каталоге данных
  (`DataDirectory.databaseFile()`). Выбор пути, «Создать базу…», «Открыть базу
  по настройкам» и «Закрыть базу» прекращают существовать. Файловый диалог в
  приложении остаётся один — выбор места резервной копии.
- **BREAKING**: настройки расположения БД удаляются как класс: спека
  `app-settings` удаляется целиком, пункт меню «Настройки…» и окно настроек
  уходят, механизм `java.util.prefs` удаляется из кода.
- Открытие при запуске становится безусловным: после показа окна открывается
  единственная БД; файла нет — создаётся; ошибка — сообщение и работа без БД с
  возможностью «Повторить открытие».
- **BREAKING**: весь неприменённый набор миграций применяется в одной
  транзакции SQLite. Сбой — откат транзакции, файл остаётся до-миграционным.
  Механика отката из копии (атомарная замена файла, перенос WAL, временные
  `*.restore`-файлы), поколения копий с метками времени и лимитом хранения
  удаляются.
- Перед миграцией создаётся одна служебная копия фиксированного имени
  `bonds2.pre-migration.db` в каталоге данных, атомарно перезаписываемая.
- Новое поведение резервных копий: «Файл → Сделать резервную копию…» копирует
  БД командой `VACUUM INTO` в выбранное пользователем место с проверкой
  целостности. Восстановление из копии — только вручную, вне приложения
  (процедура в README); код восстановления в приложении отсутствует.

## Capabilities

### New Capabilities

— (новых возможностей нет; резервное копирование — поведение хранилища и
  ложится в существующую capability `sqlite-persistence`)

### Modified Capabilities

- `app-settings`: все три требования удаляются, capability прекращает
  существование после синхронизации.
- `main-window`: пункты меню работы с БД заменяются («Сделать резервную
  копию…», «Повторить открытие»); автооткрытие, создание, закрытие базы и
  чтение настроек удаляются; безусловное открытие единственной БД при запуске;
  подтверждение миграции и индикатор состояния переработаны (без пути и без
  восстановления из копии); из требований завершения убираются упоминания
  создания и записи настроек.
- `database-lifecycle`: операция создания по произвольному пути удаляется;
  открытие работает только с единственным файлом и создаёт его при отсутствии;
  резервное копирование становится операцией сервиса; из типизированных причин
  отклонения уходит «файл существует».
- `sqlite-persistence`: инициализация и миграции переописаны вокруг
  единственной БД и одной транзакции набора; откатная механика и хранение
  поколений копий удаляются; добавлены резервная копия по указанию
  пользователя, служебная копия перед миграцией и восстановление вручную.

## Impact

- Код: `dbservice/DatabaseService` (API `open`/`create`, `RejectionCause`),
  `persistence/` (`Database`, `BackupManager` — сжимается, `SchemaInspector` —
  уход от Flyway API, `SqliteSupport`), удаление `settings/` (4 файла),
  `files/StampedFiles`, `ui/SettingsDialog`, части `ui/DatabaseController` и
  `ui/MainWindowApp`.
- Зависимости: Flyway удаляется из сборки; механизм миграций — собственный
  прогон скриптов `classpath:db/migration` с преемственностью таблицы
  `flyway_schema_history` существующих БД.
- Тесты: удаление тестов настроек и создания; новые тесты единого открытия,
  транзакционности набора миграций, служебной и пользовательской копий; пороги
  покрытия и мутаций (`coverage.minLine=0.80`, `mutation.threshold=70`)
  сохраняются.
- README: процедура ручного восстановления из копии, расположение единственной
  БД.

## Вне рамок изменения

- Архитектурный слой ядра приложения (composition root, конвейер запуска,
  инверсия входа UI) — отдельное изменение `app-core`.
- Упрощение семантики остановки `DatabaseService` (повторные остановки, сроки)
  — кандидат на отдельное изменение.
- Цепочка выхода (`ExitCoordinator`), единственный экземпляр, `src/verified` —
  не меняются.
- Перенос данных или миграция существующих пользовательских путей БД: БД
  берётся только из каталога данных; файлы вне его не ищутся и не
  переносятся.
