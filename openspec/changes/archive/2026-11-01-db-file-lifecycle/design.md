# Design

## Context

См. `proposal.md` — мотивация и состав изменения.

Текущее состояние: `DatabaseService` принимает путь в `open(Path, boolean
createIfMissing)` и `create(Path)`; путь приходит из `Settings` (`databasePath`
или `DataDirectory.databaseFile()`); `BackupManager` создаёт штампованные копии
`.bak-*`, держит три поколения и восстанавливает файл из копии при сбое
миграции; миграции применяет Flyway по одной; распознавание состояния схемы —
через Flyway API (`SchemaInspector`). Настройки хранятся в `java.util.prefs`.

Существенная особенность SQLite, на которую опирается дизайн: DDL
транзакционен — весь набор миграций можно применить в одной транзакции, и сбой
оставит файл до-миграционным без какого-либо восстановления из копии.

## Goals / Non-Goals

**Goals:**

- Жизненный цикл файла БД сводится к одному файлу в каталоге данных и одному
  входу «открыть».
- Удалить восстановление из копии, поколения копий и настройки как класс.
- Резервное копирование — явное действие пользователя; восстановление —
  вручную вне приложения.

**Non-Goals:**

- Слой ядра приложения (composition root, конвейер запуска) — изменение
  `app-core`.
- Изменение цепочки выхода и семантики остановки сервиса.
- Перенос пользовательских БД со старых путей в каталог данных.

## Decisions

### 1. Путь БД — всегда `DataDirectory.databaseFile()`

`DatabaseService.open()` теряет параметры: файл всегда из каталога данных,
`createIfMissing` всегда истинно (открытие отсутствующего файла создаёт БД).
Каталог данных создаётся при отсутствии, как сегодня.

*Альтернатива:* сохранить настраиваемый путь — отвергнуто пользователем: выбор
пути и есть источник удаляемой сложности.

### 2. Настройки удаляются целиком

Удаляются `settings/` (`Settings`, `SettingsStore`, `SettingsValidator`,
`PreferencesBackend`), `ui/SettingsDialog`, пункт меню «Настройки…» и все
упоминания настроек в UI. Механизм `java.util.prefs` возвращается, когда
появятся реальные настройки, а не заделом.

*Альтернатива:* оставить пустой механизм настроек — отвергнуто: мёртвый код.

### 3. Миграции: собственный прогон набора в одной транзакции, Flyway удаляется

Новый прогон в `persistence` поверх `SqliteSupport`:

- список скриптов — `classpath:db/migration`, имена прежнего формата Flyway
  (`V<версия>__описание.sql`), сортировка по версии;
- применённые версии читаются из существующей таблицы
  `flyway_schema_history` — преемственность уже развёрнутых БД;
- применение: `BEGIN` → каждый неприменённый скрипт по порядку → `INSERT`
  строки истории → `COMMIT`; любая ошибка (скрипт или запись истории) —
  `ROLLBACK`, файл остаётся до-миграционным;
- `SchemaInspector` переписывается на прямое чтение таблицы истории: семантика
  состояний (пустой, чужой, актуален, нужна миграция, новее приложения)
  сохраняется, источник — таблица истории и список скриптов;
- соединения миграций — с внешними ключами и полным sync (существующее
  требование), режим журнала не меняется (внутри транзакции и нельзя).

Контрольные суммы применённых миграций не проверяются: раннер читает только
версии. Зафиксировано в Risks.

*Альтернатива:* остаться на Flyway с по-миграционными транзакциями —
отвергнуто: частичное применение набора требует восстановление из копии,
которое удаляется.

### 4. Служебная копия перед миграцией: фиксированное имя, атомарная перезапись

Файл `bonds2.pre-migration.db` в каталоге данных. Порядок: `VACUUM INTO` во
временный файл в том же каталоге → `PRAGMA integrity_check` → сброс на диск
(`FileChannel.force(true)`, канал закрыт до перемещения — на Windows
перемещение открытого файла ненадёжно) → `Files.move(..., ATOMIC_MOVE,
REPLACE_EXISTING)`. Переименование внутри одного каталога атомарно на Linux,
macOS и Windows — поведение одинаково.

Поведение при сбое: не создалась копия или не прошла проверку — временный
файл удаляется, прежняя служебная копия остаётся, миграция не выполняется,
файл БД не меняется, пользователю — ошибка. Отката нет и не нужно: сбой
миграции откатывает транзакция (решение 3).

*Альтернатива:* копия с меткой времени и лимитом поколений (текущее) —
отвергнуто; отказ от копии вовсе — отвергнуто: страховка от успешной, но
ошибочной миграции обязательна правилами проекта.

### 5. Резервная копия пользователю: `VACUUM INTO` без частичной цели

Меню «Сделать резервную копию…» открывает единственный в приложении диалог
выбора места. Копия пишется во временный файл рядом с целью (цель может быть
на другой файловой системе), проверяется, сбрасывается на диск и заменяет цель
(`ATOMIC_MOVE` при возможности, иначе обычное перемещение с `REPLACE_EXISTING`
— решение о замене подтверждает сам диалог сохранения).

Поведение при сбое: временный файл удаляется, цель остаётся прежней (или
отсутствует, если её не было), пользователю — классифицированная причина
(занято, нет места, недоступен путь). Приложение не учитывает и не удаляет
пользовательские копии.

*Альтернатива:* автоматические копии по расписанию — отвергнуто:
ответственность пользователя, явно выраженная в решении.

### 6. API сервиса: `backup(Path)` как операция, `create` удаляется

`DatabaseService`: `open()` без параметров; `create(Path)` и
`RejectionCause.FILE_EXISTS` удаляются; `backup(Path target)` становится
операцией очереди сервиса — строго последовательно с открытием, закрытием и
миграцией, доступна при открытой БД. Тестовый шов `Storage` обновляется под
новый набор операций. `StatusText` упрощается: путь не показывается.

### 7. UI: меню и диалоги

Меню «Файл»: «Сделать резервную копию…» (доступна при открытой БД), «Повторить
открытие» (доступна, когда БД не открыта и не идёт операция), «Выход».
Открытие при запуске — безусловное. Текст диалога миграции дополняется
служебной копией; сценарий «неудачная миграция» больше не восстанавливает
файл — он не изменился.

*Альтернатива:* сохранить окно настроек с просмотром пути — отвергнуто:
окно упразднено решением пользователя.

## Risks / Trade-offs

- [БД пользователя лежала вне каталога данных] → после обновления приложение
  создаст новую пустую БД; прежний файл не тронут. Смягчение: README
  описывает возврат — скопировать файл в каталог данных при закрытом
  приложении. Осознанное BREAKING-последствие.
- [Контрольные суммы истории не проверяются] → вручную изменённая таблица
  истории не обнаружится. Смягчение: таблица — внутренняя деталь приложения,
  README это фиксирует; версии читаются как есть.
- [Откат версии приложения после миграции] → «схема новее приложения»,
  открытие отклоняется. Поведение существующее, не меняется.
- [Старые файлы `*.bak-*` и `*.restore`] → остаются на диске без действий
  приложения; пользователю о них в README.

## Migration Plan

Развёртывание — обычный запуск новой версии: файл в каталоге данных либо
открывается, либо создаётся. Автоматических преобразований нет. Откат на
старую версию: та же БД открывается, пока версия схемы ей известна; после
применённых миграций — отклонение по «схема новее приложения». Служебная
копия `bonds2.pre-migration.db` позволяет вернуть состояние до миграции
вручную.
