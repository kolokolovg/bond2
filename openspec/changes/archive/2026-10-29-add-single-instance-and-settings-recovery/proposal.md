# Proposal

## Why

Два одновременно запущенных экземпляра приложения конфликтуют за один файл БД (WAL, миграция с резервной копией, закрытие с checkpoint) и за файл настроек. Кроме того, повреждённый файл настроек сейчас молча заменяется значениями по умолчанию без следа, а относительный путь к БД незаметно превращается в путь по умолчанию — пользователь может открыть не ту базу и потерять исходные настройки при следующем сохранении.

## What Changes

- Приложение берёт эксклюзивную блокировку файла `bonds2.lock` в каталоге данных приложения до чтения настроек. Если блокировка занята, показывается сообщение «уже запущено», приложение завершается без открытия БД.
- При обнаружении испорченного файла настроек (нечитаем, битая Unicode-последовательность, относительный или некорректный путь, флаг не `true`/`false`) он молча копируется в `settings.properties.bad-<yyyyMMdd-HHmmss>` и перезаписывается значениями по умолчанию.
- Отсутствующий файл, отсутствующие ключи и пустой путь испорченными не считаются.
- Сбой копирования или записи при восстановлении не мешает запуску: используются значения по умолчанию, ошибка пишется в лог.

## Capabilities

### New Capabilities
- `single-instance`: гарантия одного работающего экземпляра приложения на каталог данных.

### Modified Capabilities
- `app-settings`: уточняется понятие повреждённого файла настроек и его восстановление с резервной копией.
- `main-window`: запуск второго экземпляра завершается сообщением без главного окна.

## Impact

- Код: `MainWindowApp.start/stop`, новый класс блокировки в `persistence` или рядом с `DataDirectory`, `SettingsStore.load`, `Settings.parseDatabasePath` (различение «пусто» и «некорректно»).
- Новый файл `bonds2.lock` в каталоге данных; новые файлы `settings.properties.bad-*`.
- Тесты: подпроцесс для проверки блокировки, тесты восстановления настроек. Зависимости не меняются.
- Вне объёма: активация окна первого экземпляра, ротация и очистка старых копий настроек.
