# Design

## Context

Пути завершения сегодня: «Файл → Выход»/закрытие окна → `DatabaseController.requestExit()`
(неблокирующая цепочка) → `Platform.exit()` → `MainWindowApp.stop()` → блокирующий
`DatabaseController.shutdown()` на потоке JavaFX (5 c, при миграции до ~65 c) →
`InstanceLock.close()`. Внешнее завершение (SIGTERM) → хук `bonds2-shutdown` →
`externalStop` = `db.shutdown(STOP_TIMEOUT)` — только сервис БД, только 5 c. Запись
настроек идёт на потоке-демоне `bonds2-settings` и перед смертью процесса не
ожидается. Мотивация — в `proposal.md` (Why).

## Goals / Non-Goals

**Goals:**

- Освободить поток JavaFX при завершении, сохранив порядок: остановка БД → ожидание
  записи настроек → освобождение блокировки экземпляра → смерть процесса.
- Показывать пользователю истечение срока остановки в пути через меню; журналировать в
  остальных путях.
- Дождаться незавершённой записи настроек (не дольше 5 c) во всех путях выхода.

**Non-Goals:**

- Изменение таймаутов остановки БД (30 c / 5 c / 30 c) и семантики `DatabaseService`
  (спека `database-lifecycle` не меняется, поток `bonds2-db` остаётся демоном).
- Отклонение ожидающей миграции в хуке внешнего завершения (вне рамок, см. proposal).
- Любые изменения форматов файлов, схемы БД, блокировки экземпляра.

## Decisions

### 1. Поток завершения вместо блокировки `stop()`

`MainWindowApp.stop()` запускает выделенный поток завершения `bonds2-exit`
(не демон) и возвращается сразу. Поток выполняет всю цепочку, которая сейчас живёт в
`DatabaseController.shutdown()`: остановка сервиса (`STOP_TIMEOUT`), при `REFUSED` —
отказ/ожидание миграции (`MIGRATION_TIMEOUT`) и повторная остановка, затем ожидание
записи настроек, затем `InstanceLock.close()`, затем `setExternalStop(null)`. Процесс
не умирает раньше времени, потому что поток не демон; после его окончания не остаётся
недемоновых потоков, JVM завершается сама с кодом 0.

- Альтернатива: сохранить блокировку `stop()`, но ограничить общее время (например,
  5 c). Отвергнута: JVM умирает с незакрытой БД; прерывать миграцию хуже ожидания —
  теряется гарантия «файл не тронут» у отката.
- Альтернатива: сделать поток `bonds2-db` недемоном на время остановки. Отвергнута:
  меняет семантику сервиса; требование «Остановка сервиса» в `database-lifecycle`
  прямо требует поток-демон.

Запуск потока идемпотентен (`AtomicBoolean`): повторный `stop()`/`Platform.exit()` не
создаёт второй поток. Гонка с хуком безопасна: остановка сервиса идемпотентна
(`shutdownAsync` возвращает тот же future), блокировка и `setExternalStop(null)` —
последние шаги потока завершения.

### 2. Тело цепочки остаётся в `DatabaseController`

Метод `shutdown()` разбивается: тело цепочки (без ожидания на вызывающем потоке)
выносится в метод, выполняемый потоком завершения; `stop()` лишь запускает его.
`MigrationFlow.cancelDialog()` — это `CompletableFuture.cancel(true)`, потокобезопасно и не
трогает JavaFX, окно к этому моменту уже скрыто тулкитом.

- Альтернатива: перенести цепочку в `DatabaseService` (без интерфейса). Отвергнута:
  владение диалогом миграции и настройками — у контроллера и его компонентов
  (`MigrationFlow`, `SettingsPersistence`); пришлось бы менять спеку сервиса.

### 3. Истечение срока в меню-пути — диалог, затем выход

В `onExitResult` результат `TIMED_OUT` показывает предупреждение (текст: БД могла
закрыться не полностью, данные не потеряны и восстановятся при следующем открытии) и
завершает приложение после подтверждения. Диалог показывается без вложенного цикла
событий, как остальные диалоги; флаг `exiting` остаётся установленным, повторные
запросы выхода игнорируются. `STOPPED` — выход как сейчас; `REFUSED` — без изменений.

- Альтернатива: только запись в журнал. Отвергнута: пользователь не узнаёт о риске;
  выбор зафиксирован как допущение в proposal (уточняется при ревью).
- В пути в обход меню и в хуке диалог невозможен (окно скрыто, тулкит мёртв) —
  событие журналируется на уровне контроллера в дополнение к журналу сервиса.

### 4. Ожидание записи настроек — `awaitTermination` с сроком 5 c

`SettingsPersistence.stopWriting()` после `shutdown()` вызывает `awaitTermination(5 c)`; по
истечении срока — запись в журнал (`WARNING`) и продолжение завершения. Ожидание
выполняется в конце цепочки потока завершения (покрывает и меню-путь: он тоже
проходит через `stop()`), а также в хуке: `externalStop` расширяется с «остановить
сервис» до «остановить сервис, затем дождаться записи настроек». Бюджет хука вырастает до
~10 c (5 c БД + 5 c настройки) — обновить README.

- Альтернатива: не ждать записи в хуке. Отвергнута: SIGTERM во время записи — именно
  случай потери последнего сохранения (сценарий «Внешнее завершение во время записи
  настроек»).
- Поведение при сбое: файл остаётся целым в любом случае — запись настроек уже
  делает fsync временного файла и атомарную замену; ожидание лишь даёт ей доделать
  работу. Отката не требуется. Прерывание потока записи не используется.

### 5. Платформы

Изменение чисто потоковое: пути, файлы и блокировки не меняются. Порядок
«остановка БД → запись настроек → блокировка» одинаков на Linux, macOS и Windows;
блокировка при аварийной смерти процесса по-прежнему освобождается ОС, файл
`bonds2.lock` не удаляется. Код выхода процесса 0 сохраняется (JVM завершается
штатно после конца потока завершения).

## Risks / Trade-offs

- [Поток завершения зависает] → все ожидания в цепочке ограничены сроками (как
  сегодня, суммарно ~65 c в худшем случае), примитивы те же; нового неблокированного
  кода нет.
- [Пользователь видит скрытое окно, а процесс ещё жив] → окно скрывает JavaFX до
  `stop()`; процесс заканчивается сразу за цепочкой; заметно только в списке процессов.
- [Тесты, полагающиеся на блокирующий `stop()`] → поток завершения создаётся через
  внедряемую фабрику/исполнитель, тесты запускают цепочку синхронно и дожидаются
  future; `MainWindowAppTest.shutdownStopsDatabaseBeforeReleasingLock` переводится на
  новый контракт.
- [Покрытие pitest нового кода] → логика ожиданий выносится в тестируемые методы без
  реальных задержек (внедряемые таймауты), как принято в проекте.
