# Design

## Context

Отклонения операций жизненного цикла сегодня представляются записями `OpenResult.Rejected(String message)` и `CloseResult.Rejected(String message)`; причины различимы только подстрокой в тексте (см. proposal.md — Why). Производятся они в 9 точках `dbservice`: `OpenFailures.notAllowed(...)` ×5 (состояние), `MESSAGE_STOPPED` ×2 напрямую и ×2 через функциональный параметр `submit(..., Function<String, T> rejection)` (остановка), `OpenFailures.fileExists(...)` ×1. Разбор — в `DatabaseController.onCreateResult` (`isStateOrStoppingRejection`). Хранилище, миграции, файловые операции и потоковая модель не затрагиваются.

## Goals / Non-Goals

**Goals:**

- Причина отклонения становится значением, по которому потребитель различает отклонения без разбора текста.
- Производство причин сосредоточено в `dbservice` так, чтобы новую точку отклонения нельзя было добавить без выбора причины.
- Тесты утверждают поведение (один фоновый поток операций, запись настроек вне потока JavaFX), а не имена потоков.

**Non-Goals:**

- Изменение текстов сообщений, политики показа диалогов или набора различаемых причин.
- Типизация причин *сбоев* (`OpenResult.Failed.reason` — отдельная ось, не меняется).
- Разбиение `DatabaseControllerTest`, чистка мёртвого кода, изменения `StatePublisher` и остановки (другие изменения).

## Decisions

### 1. Причина — общий enum в `dbservice`

`enum RejectionCause { STATE, STOPPED, FILE_EXISTS }`; записи получают поле: `OpenResult.Rejected(RejectionCause cause, String message)`, `CloseResult.Rejected(RejectionCause cause, String message)`.

- Альтернатива: sealed-подварианты (`Rejected.State` / `Rejected.Stopped` / `Rejected.FileExists`) — строже (FILE_EXISTS у закрытия невозможен by construction), но дублирует иерархию в двух sealed-интерфейсах и правку `permits`; невыразимая комбинация на практике не встречается и закрыта тестами фабрик.
- Альтернатива: отдельные enum'ы для open/close — дублирование общего смысла.

### 2. `submit` принимает фабрику с причиной

`Function<String, T> rejection` → `BiFunction<RejectionCause, String, T>`; вызовы — `rejection.apply(STOPPED, MESSAGE_STOPPED)`. Прочие точки производства передают причину явно: `new OpenResult.Rejected(STATE, OpenFailures.notAllowed("открыть"))`, `OpenFailures.fileExists` → `FILE_EXISTS`.

- Альтернатива: промежуточная запись-носитель `Rejection(cause, message)` и `Function<Rejection, T>` — лишний тип, поля записей результата остаются плоскими.

### 3. Политика показа остаётся в UI

`onCreateResult` различает `cause`: `STATE`/`STOPPED` — тихий DEBUG-журнал (как сегодня), `FILE_EXISTS` — диалог ошибки. `onOpenResult` остаётся тихим для всех отклонений. `isStateOrStoppingRejection` удаляется.

- Альтернатива: метод `cause.isSilent()` в `dbservice` — отвергнута: решение «что показывать пользователю» принадлежит UI-слою, сервис о диалогах не знает (спека «Независимость жизненного цикла БД от интерфейса»).

### 4. Тесты потоков утверждают поведение

Вместо равенства имени потока: операции жизненного цикла выполняются все в одном потоке, не совпадающем с потоком вызывающего; запись настроек происходит вне потока JavaFX (не в потоке, выполняющем тестовое тело FX). Именование потоков в production (`SETTINGS_THREAD_NAME`, `"bonds2-db"`) сохраняется как диагностика — константы и daemon-флаг не удаляются.

- Альтернатива: удалить именование вовсе — хуже для диагностики; имена не утверждаются, значит рефакторинг имени тестов не ломает.

## Risks / Trade-offs

- [Новая точка отклонения без осмысленной причины] → конструирование `Rejected` только с явным `cause`; тест контракта перебирает все операции и их причины, pitest проверяет, что мутации значения причины убиваются.
- [Смена формы записей массово правит тесты] → правка механическая (компилятор перечисляет все места), поведение не меняется; риск регрессии снят контрактными тестами каждого вида отклонения.
- [Ошибочная причина в существующей точке] → соответствие точек и причин зафиксировано в design (п. 2) и проверяется попарными тестами: остановка сервиса → STOPPED, неверное состояние → STATE, существующий файл → FILE_EXISTS.

Файловые операции, хранение и миграции не затрагиваются: поведение при сбое и откат не меняются; специфика платформ (Linux/macOS/Windows) не вступает в игру.

## Migration Plan

Одно изменение, развёртывание — обычная сборка (`./gradlew check -Pheadless=true`, затем `pitest` — затронута логика сервиса БД). Внешних потребителей API нет, формат хранения не меняется. Откат — revert изменения целиком.
