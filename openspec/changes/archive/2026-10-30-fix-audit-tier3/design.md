# Design

## Context

Тир 3 аудита (см. proposal.md — Why). Сайты: DatabaseService.java:183 (срок остановки без проверки), StatePublisher.java:61 (дубликаты подписок), таксономия OpenFailures/ErrorMessages (только текст причин, коды SQLite не читаются), DatabaseController.java:152 (чтение настроек на FX-потоке) и 193/206 (гарды отстающего состояния), MainWindowApp.java (диалог создания без дописывания расширения, отсутствие хука завершения в Main.java). Хук завершения и поведение `stop()` связаны: `stop()` остаётся последней линией внутри JavaFX, хук — снаружи.

## Goals / Non-Goals

**Goals:**

- Каждая из восьми находок тира либо закрыта кодом, либо осознанно принята с зафиксированным обоснованием.
- Новые поведения минимально заметны пользователю: понятнее сообщения, аккуратнее диалог создания, отзывчивее запуск.

**Non-Goals:**

- Тир 4 (задачи сборки Gradle) — отдельное изменение.
- Неблокирующий `stop()` (см. D5) и любые изменения таймаутов остановки сверх валидации срока.
- Классификация всех кодов SQLite: только практически встречающиеся при открытии/создании/миграции локального файла.

## Decisions

### D1. Неположительный срок остановки — ошибка программиста

`shutdown(Duration)` и `shutdownAsync(Duration)` первым делом проверяют `timeout.isZero() || timeout.isNegative()` и бросают `IllegalArgumentException` с сообщением о положительном сроке. Проверка до захвата `shutdownLock`: состояние сервиса не меняется, `stopping` не выставляется.

- Альтернатива: трактовать ноль как «немедленно» и честно докладывать TIMED_OUT — отвергнута: ноль почти всегда ошибка вычисления срока (например, `Duration.between` с перевёрнутыми аргументами), молчаливая покинутость операций маскирует её.
- Альтернатива: клампить к минимуму — отвергнута по той же причине.

### D2. Классификация сбоев SQLite по коду результата

В таксономии сбоев (OpenFailures/ErrorMessages) причины открыт��я/создания/миграции дополняются разбором `SQLException.getErrorCode()` из цепочки причин: `SQLITE_BUSY`/`SQLITE_LOCKED` — «БД занята другим процессом… повторите позже» (повторимая), `SQLITE_CORRUPT` — повреждение, `SQLITE_FULL` — отсутствие места, `SQLITE_CANTOPEN`/`SQLITE_IOERR` — невозможность работы с файлом. Коды, не входящие в набор, оставляют сегодняшнюю классификацию по месту возникновения.

- Альтернатива: разбор текста сообщения драйвера — отвергнут: текст зависит от версии драйвера и не стабилен.
- Поведение при сбое: код результата отсутствует (0) или неизвестен — путь идентичен сегодняшнему; новые причины несут понятный текст без стеков.
- Риск: не всякая SQLException драйвера несёт корректный код — fallback гарантирует отсутствие регресса.

### D3. Повторная подписка — `onError` по контракту Flow

В `StatePublisher.subscribe` перед регистрацией проверяется наличие подписки этого подписчика; при повторе вызывается `subscriber.onError(new IllegalStateException(...))`, подписчик не добавляется. Хранение: множество подписчиков остаётся списком, проверка линейна — подписчиков единицы.

- Альтернатива: игнорировать повторную подписку молча — отвергнута: прямое нарушение контракта `java.util.concurrent.Flow.Publisher`.
- Альтернатива: замена существующей подписки — отвергнута: контракт предписывает `onError`.

### D4. Чтение настроек до сборки интерфейса, вне FX-потока

`MainWindowApp.start` выполняет чтение настроек в фоновом потоке (load завершён → `Platform.runLater`: создание контроллера с готовым `LoadResult`, сборка меню, показ окна, `openOnStartup`). Конструктор `DatabaseController` принимает готовый `LoadResult` вместо чтения `store.load()` самого. Окно появляется после чтения: на быстром локальном диске — незаметно, на медленном — позже, но без заморозки потока интерфейса.

- Альтернатива: окно сразу, настройки догружаются и обновляют состояние — отвергнута: автооткрытие и предупреждение о сбросе зависят от настроек, потребовалась бы вторая фаза инициализации с промежуточным состоянием интерфейса.
- Поведение при сбое чтения: сегодня `SettingsStore.load` не бросает (восстановление встроено, возвращает значения по умолчанию с признаком сброса) — контракт сохраняется.

### D5. Блокирующий `stop()` остаётся — принято без изменения кода

К моменту `stop()` окно уже скрыто JavaFX: никакая обратная связь пользователю невозможна. Неблокирующий вариант (вернуться из `stop` до закрытия БД) позволяет процессу завершиться с незакрытой БД — это хуже короткой задержки. Ожидание остаётся ограниченным (5 с обычно, до 65 с при миграции), обоснование фиксируется в javadoc метода.

- Альтернатива: неблокирующий `stop` с фоновым ожиданием — отвергнут по причине выше.

### D6. Хук завершения JVM в `Main`

`Runtime.getRuntime().addShutdownHook` регистрируется в `main` до `Application.launch`: поток-хук проверяет флаг остановки контроллера/сервиса и, если сервис ещё работает, выполняет ту же лучшую попытку остановки с коротким сроком (5 с), без касания JavaFX (`Platform.runLater` в хуке недопустим — приложение может быть уже мертво). Идемпотентность со штатным выходом: `requestExit` уже останавливает сервис, хук видит остановленный сервис и завершается мгновенно.

- Альтернатива: не добавлять (WAL-recovery достаточно) — отвергнуто: checkpoint при закрытии выполняется только при явном закрытии; без хука внешний kill оставляет журнал и никогда не проверяет целостность при выходе.
- Поведение при сбое: любые ошибки остановки в хуке журналируются и не мешают завершению; хук не продлевает жизнь процессу сверх срока.
- Платформы: сигналы завершения (SIGTERM, конец сессии, остановка из IDE) доставляются одинаково; SIGKILL не перехватывается ничем — зафиксировано в спеке.

### D7. Диалог создания: дописывание `.db` и честное сообщение

`chooseNewDatabase` после выбора проверяет расширение результата и дописывает `.db`, если его нет. Сообщение о существующем файле переформулируется: перезапись не выполняется, выберите другое имя (сегодняшний вопрос диалога «перезаписать?» остаётся — его текст контролирует JavaFX, убрать нельзя, но противоречие снимается пояснением). Формулировки сообщений — на ревью дизайнером при применении.

- Альтернатива: свой диалог имени файла — отвергнут: дублирование платформенных диалогов ради одного вопроса.

### D8. Признак идущей операции в контроллере

`DatabaseController` хранит `boolean busy` (или ссылку на незавершённый future открытия/создания): `open`/`createDatabase` игнорируют повторный запрос, пока операция не завершена; сброс — в обработчике результата на FX-потоке. Гард по отстающему состоянию остаётся как второй рубеж.

- Альтернатива: полагаться только на отказ сервиса — отвергнуто: работает, но держит инвариант на неявной конвенции тихих отказов (находка №15).

## Risks / Trade-offs

- [R1: `getErrorCode` не заполнен в части исключений драйвера] → fallback на сегодняшнюю классификацию; тесты прогоняют реальные коды через занятую БД.
- [R2: окно при запуске появляется позже на медленном диске] → осознанный обмен заморозки на задержку; на локальном диске чтение микросекундное.
- [R3: хук завершения конфликтует со штатным выходом] → двойная остановка невозможна (повторная `shutdownAsync` возвращает тот же future); хук не трогает UI-потоки.
- [R4: pitest на новых ветках (валидация срока, коды, дубликаты)] → каждая ветка покрыта тестом в своих задачах; порог 70%.

## Migration Plan

Изменение кодовое, форматы файлов не затрагиваются. Откат — revert. Новые сообщения пользователей появляются только в соответствующих сценариях сбоев.
