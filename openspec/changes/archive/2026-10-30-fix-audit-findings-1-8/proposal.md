# Proposal

## Why

Аудит кода (проверка по исходникам всех четырёх зон: persistence, dbservice, ui, settings)
выявил восемь дефектов, из которых два нарушают обещания, данные пользователю в README и
спеках: молчаливое создание пустого файла БД на месте удалённого при миграции, и молчаливый
сброс пользовательского пути из-за BOM в файле настроек. Остальные шесть — нарушения
собственных инвариантов жизненного цикла (незакрываемое приложение при сбое цепочки выхода,
залипающее состояние «открыта» после остановки сервиса, хрупкая публикация состояний) и
проблемы диагностики и отзывчивости интерфейса.

## What Changes

1. **Миграции и инициализация не создают отсутствующий файл БД** (аудит №1). Соединения
   Flyway получают те же свойства «только существующий файл», что и остальные соединения
   пакета persistence; файл, удалённый между проверкой резервной копии и применением
   миграций, даёт ошибку вместо молчаливого создания пустой мигрированной базы.
2. **Файл настроек с UTF-8 BOM читается корректно** (аудит №2). Ведущий U+FEFF срезается
   при чтении; ключи распознаются, пользовательский путь не подменяется значениями по
   умолчанию.
3. **Сбой цепочки выхода не делает приложение незакрываемым** (аудит №3). При
   исключении из future остановки флаг выхода сбрасывается, пользователю показывается
   ошибка; повторный запрос выхода работает.
4. **Гонка «покинутой» операции закрыта** (аудит №4). Результат операции, завершившейся
   в момент истечения срока остановки, не публикуется ни при каком интерливинге:
   итоговое состояние — «закрыта», БД закрывается тихо.
5. **Публикация состояний переживает сбой подписчика** (аудит №5). `Error` из
   `onNext` подписчика не оставляет подписку мёртвой и не «кирпичит» сервис в состоянии
   «открывается»: флаг доставки сбрасывается в `finally`, сбойный подписчик отменяется,
   остальные продолжают получать состояния.
6. **Отклонение создания БД из-за гонки состояния — тихое** (аудит №6). `Rejected` при
   создании обрабатывается как при открытии: журналирование без диалога ошибки;
   диалог остаётся только для действительных ошибок.
7. **Сообщение об ошибке содержит первопричину** (аудит №7). Текст ошибки собирается по
   цепочке причин до первого непустого сообщения (включая `SQLException.getNextException()`),
   а не только с одного уровня.
8. **Чтение и запись настроек — вне потока интерфейса** (аудит №8). `load`/`save` настроек
   выполняются на фоновом исполнителе с возвратом результата в поток JavaFX; интерфейс
   не замерзает на время fsync.

Несовместимых изменений (**BREAKING**) нет: форматы файлов, ключи настроек, публичные API
и результаты операций не меняются; все восемь пунктов — устранение дефектов и укрепление
существующего поведения.

## Capabilities

### New Capabilities

Нет: все восемь пунктов ложатся на существующие возможности.

### Modified Capabilities

- `sqlite-persistence`: требование «Служебные операции не создают файл БД» расширяется
  на применение миграций и инициализацию схемы — гарантия «отсутствующий файл не
  воссоздаётся» действует и для соединений Flyway (аудит №1).
- `app-settings`: «Сохранение настроек» — файл с UTF-8 BOM читается без сброса (аудит №2);
  «Окно настроек» — сохранение не блокирует поток интерфейса дисковым вводом-выводом
  (аудит №8).
- `database-lifecycle`: «Остановка сервиса» — крайний интерливинг истечения срока
  (операция завершается в окне проверки) закреплён сценарием (аудит №4); «Публикация
  состояния» — сбой подписчика при доставке не прекращает публикацию (аудит №5), сообщение
  об ошибке включает первопричину из глубины цепочки (аудит №7).
- `main-window`: «Пункт меню „Выход“» — сбой цепочки выхода восстанавливает возможность
  выхода (аудит №3); «Пункты меню настроек и открытия БД» — тихая обработка отклонения
  создания из-за гонки состояния (аудит №6).

## Impact

- **Код**: `persistence/SchemaInspector.java` (свойства соединений Flyway), возможно
  `persistence/SqliteSupport.java` (общий конструктор no-CREATE-свойств) и
  `persistence/BackupManager.java`, `persistence/Database.java` (проверка файла после
  миграции); `settings/SettingsStore.java` (срез BOM); `dbservice/StatePublisher.java`
  (сброс флага доставки, обработка `Error`); `dbservice/DatabaseService.java`
  (перепроверка `abandoned`, публикация «закрыта» при пробое `Error`);
  `dbservice/ErrorMessages.java` (обход цепочки причин); `ui/DatabaseController.java`
  (восстановление цепочки выхода, тихий `Rejected` создания, асинхронные настройки),
  возможно `ui/MainWindowApp.java` (фоновой чтение настроек при старте).
- **Тесты**: `DatabaseMigrationTest`, `SqliteSupportTest`, `SettingsStoreTest`,
  `StatePublisherTest`, `DatabaseServiceTest`, `ErrorMessagesTest`, `DatabaseControllerTest`,
  `SettingsDialogTest`, `MainWindowAppTest` — новые сценарии для каждого пункта и
  обновление зафиксированных текущим поведением тестов (BOM, `causeWithoutMessageIsIgnored`,
  обработка `Rejected` при создании).
- **Зависимости**: новые зависимости не вводятся.
- **README**: обновляются формулировки разделов «Хранилище данных», «Настройки и база
  данных» там, где поведение закреплено документом (гарантия no-CREATE при миграции,
  чтение BOM).

## Out of Scope

- Находки аудита №9–№16 (низкий приоритет): переполнение `(int) busyTimeout`, окно WAL в
  `restore`, бесконечный цикл подбора имени копии, fallback для `ATOMIC_MOVE`,
  `InterruptedException` как `TIMED_OUT`, ложное «Сервис БД остановлен.» в окне отката,
  tooling-правки `build.gradle.kts`, сброс всего файла при одном плохом ключе.
- Рефакторинг `StatePublisher` до полного соответствия спецификации Reactive Streams
  (`onError` при `request(n <= 0)`, `onError` вместо тихой отмены бросающего подписчика).
- Блокировка FX-потока в `stop()` при завершении в обход меню во время миграции —
  осознанный компромисс, задокументирован в коде.
- Отписка `StateSubscriber` и пересоздание контроллера — актуально только при будущем
  рефакторинге жизненного цикла окна.
