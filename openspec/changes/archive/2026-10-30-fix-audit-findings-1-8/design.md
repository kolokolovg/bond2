# Design

## Context

См. `proposal.md` (Why, What Changes). Ключевые обстоятельства реализации: в пакете
`persistence` уже существует единая точка создания соединений `SqliteSupport` со свойствами
«только существующий файл»; исключение — `SchemaInspector.flyway()`, который настраивает
Flyway через URL и получает соединения с правом создания файла. `StatePublisher` —
единственная реализация `Flow.Publisher` в приложении, подписчик один (`StateSubscriber`,
переносит доставку в поток JavaFX). Контроллер интерфейса хранит флаги жизненного цикла
выхода, доступные только из потока JavaFX. Спека-дельты закрепляют поведение; здесь —
как именно оно достигается.

## Goals / Non-Goals

**Goals:**

- Гарантия «отсутствующий файл не воссоздаётся» действует для всех соединений с БД,
  включая соединения Flyway (чтение истории, применение миграций, инициализация).
- Публикация состояний и жизненный цикл выхода восстанавливаются после любого сбоя,
  включая `Error` и исключения в самой цепочке остановки.
- Интерфейс не блокируется дисковым вводом-выводом настроек при сохранении.

**Non-Goals:**

- Перенос чтения настроек при старте в фон: чтение происходит до показа окна и не влияет
  на отзывчивость; вернуться к вопросу, если задержка старта станет заметна.
- Полное соответствие `StatePublisher` спецификации Reactive Streams (`onError` при
      `request(n <= 0)` и т. п.) — см. proposal, Out of Scope.
- Изменение формата файла настроек, имён резервных копий, публичных API.

## Decisions

### D1. No-CREATE для Flyway на уровне DataSource (аудит №1)

`SchemaInspector` перестаёт настраивать Flyway строкой URL: два фабричных метода —
`flywayExisting` (соединения через `SqliteSupport` со свойствами «только существующий
файл», для `inspect`, `migrateWithBackup` и `initialize`) и `flywayCreating` (текущее
поведение через URL, только для `Database.create`, где создание файла — само назначение).
DataSource — минимальная собственная реализация в `persistence`, отдающая новое соединение
на каждый вызов; новых зависимостей не вводится.

- Альтернатива: перепроверять существование/размер файла после `migrate()` и падать при
  расхождении. Отклонена: окно TOCTOU остаётся между миграцией и проверкой, а молча
  созданный файл пришлось бы чистить по путям ошибок.
- Альтернатива: проверка `Files.exists` непосредственно перед `migrate()`. Отклонена:
  окно лишь сужается; гарантия на уровне соединения закрывает все интерливинги разом и
  совпадает с принятым в проекте образцом (все прочие соединения уже так устроены).

Поведение при сбое: файл удалён до соединения — ошибка открытия соединения, миграция
падает, файл не создаётся. В `BackupManager.migrateWithBackup` перед попыткой отката
проверяется наличие основного файла: если его нет, откат не запускается (восстанавливать
нечего, checkpoint по отсутствующему файлу всё равно упадёт), выбрасывается ошибка
«файл БД не найден, миграция не выполнена» с путём к сохранённой копии. Копия и лимит
копий не затрагиваются. Чтение истории (`flyway.info()`/`validate` в `inspect`) получает
ту же гарантию: файл, удалённый после чтения схемы, даёт ошибку распознавания, а не
пустую базу со статусом «нужна миграция».

Платформы: флаг режима открытия — свойство драйвера, поведение одинаково на Linux, macOS,
Windows; работа с путями не меняется.

### D2. Срез ведущего U+FEFF при чтении настроек (аудит №2)

`SettingsStore.load` читает файл через `PushbackReader`: первый символ `U+FEFF` снят
перед передачей в `Properties.load`. Остальная логика (признаки повреждения, recover,
копия `.bad-*`) не меняется: файл с BOM и корректными ключами читается как валидный,
файл с BOM и мусором остаётся повреждённым.

- Альтернатива: считать BOM признаком повреждения и запускать recover. Отклонена:
  содержимое валидно, recover молча сбрасывает пользовательский путь — это и есть
  устраняемый дефект.
- Альтернатива: BOM-aware декодер из JDK. Отклонена: в `java.nio` такого декодера нет,
  срез одного символа проще и достаточно.

Платформы: BOM появляется в файлах, сохранённых Windows-редакторами (PowerShell 5.1,
старый Блокнот); на Linux/macOS файлы без BOM проходят мимо среза без изменений.

### D3. Восстановление цепочки выхода (аудит №3)

Обработчик сбоя в `DatabaseController.deliverExitResult` переводит обработку в поток
JavaFX: сбрасывает `exiting`, показывает диалог ошибки с текстом из `ErrorMessages`.
Приложение остаётся живым, повторный «Выход» начинает цепочку заново.

- Альтернатива: после журналирования принудительно завершать приложение. Отклонена:
  маскирует сбой и лишает пользователя шанса закрыть БД штатно; сервис после сбоя
  остановки, как правило, ещё работоспособен.

### D4. Гонка «покинутой» операции (аудит №4)

Два уровня защиты. Первый: в `DatabaseService.finish` флаг `abandoned` перепроверяется
непосредственно перед каждой публикацией результата — типовой интерливинг закрывается.
Второй (самовосстановление): `runShutdown` в конце остановки публикует «закрыта», если
последнее опубликованное состояние не «закрыта», независимо от `abandoned`. Даже если
узкое окно первого уровня сработает, подписчики и `state()` приходят к согласованному
финалу «закрыта», а не остаются в «открыта».

- Альтернатива: синхронизировать проверку `abandoned` с `shutdownLock` в `finish`.
  Отклонена: связывает поток жизненного цикла с замком остановки и усложняет рассуждение
  о взаимоблокировках; публикация-самолечение даёт согласованное состояние без новых
  захватов замков.
- Согласованность со спекой: «результат запоздавшей операции не публикуется» (дельта
  database-lifecycle, сценарий «Результат операции совпал с истечением срока») —
  публикует финальное «закрыта» сама остановка, как и в штатном сценарии «Поздний
  результат операции после завершения» (main-window).

### D5. Устойчивость публикации состояний (аудит №5)

`StatePublisher.Subscription.drain`: флаг `draining` сбрасывается в `finally`;
`RuntimeException` из подписчика — отмена подписки (как сейчас); `Error` — отмена
подписки, затем проброс выше (после сброса флага). Подписка не «залипает», фатальные
ошибки не поглощаются. `DatabaseService.submit`: при `Error` из операции публикуется
«закрыта» с причиной «внутренняя ошибка» (если операция не покинута), затем ошибка
передаётся в future вызывающему.

- Альтернатива: поглощать `Error` в `drain` и продолжать доставку. Отклонена: нарушает
  требование «фатальные ошибки виртуальной машины не поглощаются».
- Альтернатива: только `try/finally` без отмены подписки. Отклонена: подписчик,
  бросивший `Error`, остаётся зарегистрированным и продолжает получать состояния —
  повторные сбои.

### D6. Тихое отклонение создания БД (аудит №6)

Обработка `OpenResult.Rejected` в `onCreateResult` выравнивается с `onOpenResult`:
журналирование уровня DEBUG, без диалога. Диалог ошибки остаётся для `Failed`
(действительные ошибки файла).

- Альтернатива: блокировать пункт меню синхронно с началом операции. Отклонена:
  состояние доставляется в поток интерфейса асинхронно по устройству подписки;
  синхронизация меню — редизайн доставки состояний.

### D7. Первопричина в сообщении об ошибке (аудит №7)

`ErrorMessages.of` обходит цепочку `getCause()` (с ограничением глубины 5) и для
`SQLException` также `getNextException()`, выбирая первое непустое сообщение, ещё не
вошедшее в текст. Итог: `<текст> Причина: <первое непустое сообщение из глубины>`.

- Альтернатива: включать все сообщения цепочки. Отклонена: нечитаемая простыня в
  диалоге.
- Тест `causeWithoutMessageIsIgnored` фиксирует старое поведение и обновляется на
  новое ожидание.

### D8. Запись настроек вне потока интерфейса (аудит №8)

`DatabaseController` получает однопоточный фоновый исполнитель (демон). `saveSettings`
выполняет `store.save` на нём; применение настроек и закрытие окна настроек — по
завершении в потоке JavaFX; ошибка записи — предупреждение (поведение сохранено).
`rememberDatabasePath` идёт тем же путём. Исполнитель останавливается вместе с
остановкой контроллера в `shutdown()`.

- Альтернатива: вынести и чтение при старте. Отклонена: конструктор синхронный по API,
  чтение до показа окна не влияет на отзывчивость (Non-Goal).
- Альтернатива: использовать общий исполнитель сервиса БД. Отклонена: настройки не
  связаны с потоком жизненного цикла БД; смешение удлиняет очередь операций БД.

Платформы: сброс каталога на диск уже ограничен POSIX (на Windows каталог каналом не
открывается); перенос в фон не меняет это поведение.

## Risks / Trade-offs

- [Собственный DataSource для Flyway не проходит внутренние проверки Flyway] →
  Минимальная реализация `getConnection()`/`getConnection(url, user, pass)` и
  `unwrap` по образцу; проверяется интеграционным тестом миграции реального файла.
- [Двойная публикация «закрыта» (из `finish` и из самолечения в `runShutdown`)] →
  публикация-самолечение выполняется только когда последнее состояние не «закрыта»;
  подписчики получают дубликат только в вырожденном окне, что безвредно (состояние
  идемпотентно для UI); покрыто тестом.
- [Недетерминированный тест гонки `abandoned`] → интерливинг воспроизводится
  детерминированно: операция удерживается внутри тестовой реализации `Storage`, в это
  время `shutdownAsync` с минимальным сроком завершается таймаутом, затем операция
  отпускается.
- [Рост числа веток снижает мутационный score ниже порога 70%] → новые ветки
  сопровождаются тестами с граничными случаями; `pitest` запускается для изменённых
  пакетов до финальной проверки.
- [BOM-срез не покрывает UTF-16 и другие кодировки] → вне рамок: файл настроек
  определяется как UTF-8; UTF-16-файл остаётся повреждённым, как и сейчас.

## Migration Plan

Одноразовый релиз без изменения форматов данных. Откат — реверс коммита: файлы БД,
резервные копии и файл настроек, записанные исправленной версией, совместимы с текущей
(форматы не менялись). Обновление README — вместе с кодом, в последней группе задач.
