# Spec Delta

## MODIFIED Requirements

### Requirement: Резервная копия и откат при миграции существующей БД
Перед миграцией существующей БД система SHALL создать рядом с исходным файлом копию `VACUUM INTO`, согласованную с WAL и не зависящую от записи других соединений, и проверить её целостность, начиная с наличия файла копии. При ошибке миграции система SHALL атомарно заменить файл БД копией: временный файл сбрасывается на диск до перемещения, зафиксированные данные предварительно переносятся из WAL в основной файл по возможности (сбой переноса не отменяет восстановление: копия самодостаточна, а транзакции, оставшиеся только в WAL, теряются), сайдкары WAL удаляются, вызывающий получает исходную ошибку. Если основной файл удалён к моменту отката, восстановление SHALL NOT выполняться: ошибка называет путь к сохранённой копии для ручного восстановления. Прежние копии SHALL NOT удаляться сверх лимита.

#### Scenario: Успешная миграция
- **WHEN** миграция существующей БД завершена успешно
- **THEN** схема актуальна, резервная копия предыдущего состояния сохранена

#### Scenario: Неудачная миграция
- **WHEN** миграция существующей БД завершилась ошибкой
- **THEN** файл БД восстановлен из резервной копии: схема и данные совпадают с состоянием до миграции (побайтное совпадение с исходным файлом не требуется), вызывающему передана ошибка миграции, прежние копии не удалены сверх лимита

#### Scenario: Сбой в середине набора миграций
- **WHEN** часть миграций набора применена, а следующая завершилась ошибкой
- **THEN** БД восстановлена к состоянию до начала всей миграции, ни одна из ранее применённых в этом запуске миграций не сохраняется

#### Scenario: Копия не прошла проверку целостности
- **WHEN** проверка целостности резервной копии не вернула «ok»
- **THEN** миграция не выполняется, БД не изменяется, возвращается ошибка

#### Scenario: Не удалось создать копию
- **WHEN** резервную копию создать не удалось
- **THEN** миграция не выполняется, БД не изменяется, возвращается ошибка

#### Scenario: Данные в WAL попадают в копию
- **WHEN** перед миграцией в WAL есть зафиксированные, но не перенесённые данные
- **THEN** резервная копия содержит эти данные

#### Scenario: Checkpoint не удался
- **WHEN** при откате после неудачной миграции перенос WAL в основной файл (checkpoint) не удался, например WAL занят другим соединением
- **THEN** восстановление продолжается: файл БД атомарно заменён проверенной копией, событие записано в журнал

#### Scenario: Основной файл удалён до отката
- **WHEN** основной файл БД удалён к моменту отката после неудачной миграции
- **THEN** восстановление не выполняется, копия сохранена, ошибка называет путь к копии для ручного восстановления

#### Scenario: Сбой замены файла при откате
- **WHEN** атомарная замена файла БД копией не удалась
- **THEN** файл БД не изменён частично, временный файл удалён, ошибка содержит путь к копии для ручного восстановления; зафиксированные до попытки отката транзакции сохранены, если перенос WAL в основной файл успел выполниться

#### Scenario: Сброс временного файла на диск перед заменой
- **WHEN** выполняется атомарная замена файла БД копией
- **THEN** данные временного файла сброшены на диск до перемещения, чтобы потеря питания сразу после замены не оставила укороченный файл БД

#### Scenario: Неудачная замена не теряет данные из WAL
- **WHEN** на момент отката миграции в WAL основного файла есть зафиксированные, но не перенесённые данные и атомарная замена завершилась ошибкой
- **THEN** при повторном открытии БД эти данные доступны, если перенос WAL в основной файл выполнился до замены; если перенос не удался, транзакции, оставшиеся только в WAL, теряются — файл остаётся целым, копия доступна для ручного восстановления

## ADDED Requirements

### Requirement: Успех фиксации не зависит от закрытия соединения
После успешной фиксации транзакции сбой закрытия соединения SHALL NOT превращать операцию в ошибку: вызывающий получает результат работы. Сбой закрытия SHALL журналироваться и не подменять результат. Если не удалась сама фиксация, ошибка фиксации имеет приоритет, а сбой закрытия присоединяется к ней подавленной.

#### Scenario: Сбой закрытия после фиксации
- **WHEN** работа и фиксация транзакции успешны, а закрытие соединения бросило ошибку
- **THEN** вызывающий получает результат работы, сбой закрытия записан в журнал

#### Scenario: Сбой фиксации и закрытия
- **WHEN** фиксация бросила ошибку, и закрытие соединения тоже
- **THEN** вызывающий получает ошибку фиксации, сбой закрытия — подавленная ошибка при ней

### Requirement: Очистка временных файлов отката
Перед миграцией система SHALL удалять временные файлы отката `<имя-БД>.*.restore`, оставшиеся от прерванного прошлым запуском отката. Сбой удаления отдельного файла SHALL журналироваться и не мешать миграции.

#### Scenario: Остался файл от прерванного отката
- **WHEN** перед миграцией рядом с БД есть временный файл отката от прошлого запуска
- **THEN** он удалён до начала миграции

#### Scenario: Файл не удаляется
- **WHEN** временный файл отката занят другим процессом и не удаляется
- **THEN** миграция продолжается, событие записано в журнал

### Requirement: Целостность применения миграций
Система SHALL применять миграции соединениями с включёнными внешними ключами и полной синхронизацией с диском. Эти соединения SHALL NOT менять режим журнала файла БД.

#### Scenario: Нарушение внешнего ключа в миграции
- **WHEN** скрипт миграции вставляет строку, нарушающую внешний ключ
- **THEN** миграция завершается ошибкой и откатывается, файл остаётся до-миграционным

#### Scenario: Режим журнала не меняется
- **WHEN** выполняются миграции
- **THEN** режим журнала файла БД остаётся прежним (WAL остаётся WAL)
