# Design

## Context

Четыре дефекта тира 1 из аудита (см. proposal.md — Why). Текущее состояние: `SettingsDialog.save()` закрывает окно из колбэка записи, а `cancel()` и крестик закрывают сразу (SettingsDialog.java:128–160); `Database.run()` ловит `SQLException` от `close()` соединения тем же catch, что и ошибки транзакции (Database.java:270–282); `BackupManager.restore()` создаёт staging-файл `.restore`, который никто не чистит после краха, и прерывает весь откат при сбое `checkpoint` (BackupManager.java:241–249); `SqliteSupport.existingFileProperties()` не включает внешние ключи и полную синхронизацию для соединений Flyway (SqliteSupport.java:72–77).

## Goals / Non-Goals

**Goals:**

- Поведение окна настроек соответствует спеке `app-settings`: «Отмена» никогда не оставляет применённые изменения.
- Повторный вызов зафиксированной транзакции безопасен: успех commit не подменяется ошибкой закрытия соединения.
- Откат миграции не оставляет мусора и доводится до конца при сбое переноса WAL.
- Миграции применяются с теми же гарантиями целостности, что и транзакции данных.

**Non-Goals:**

- Настоящая отмена фоновой записи настроек (интерруптибельность `SettingsStore.save`) — при блокировке окна не нужна.
- Таймаут записи настроек и разблокировка окна по его истечении.
- Координация статических операций `Database` с открытыми экземплярами (тир 2 аудита).
- Изменение текстов сообщений пользователю, кроме состояния занятости окна настроек.

## Decisions

### D1. Окно настроек блокируется на время записи

Кнопки «Сохранить», «Отмена», «Обзор…» и поле пути переводятся в disable, на `Stage` вешается `setOnCloseRequest(consume)` на время записи; по завершении: успех — окно закрывается, ошибка — причина показывается в окне, элементы разблокируются.

- Альтернатива: настоящая отмена через `CompletableFuture.cancel` — отвергнута: запись на однопоточном исполнителе неинтеррумптибельна, отменилась бы только ещё не начавшаяся запись; начавшаяся всё равно применилась бы, ложное «отменено» осталось бы.
- Альтернатива: оставить поведение, поправить джавадок — отвергнута: нарушает требование «Окно настроек» спеки `app-settings`.
- Сбой записи: окно остаётся открытым и разблокированным, прежний файл не изменён (атомарная запись `SettingsStore` уже гарантирует целостность).
- Платформы: перехват закрытия — уровень JavaFX (`onCloseRequest`), поведение одинаково на Linux, macOS, Windows; файловых операций решение не добавляет.

### D2. Успех commit не зависит от закрытия соединения

В `Database.run()` try-with-resources разворачивается на явные фазы: после успешного `commit()` результат возвращается вызывающему, а сбой `close()` журналируется предупреждением и добавляется подавленным исключением к результату не может (результат — значение `T`), поэтому только журнал. Если упал `commit` или работа — действует прежний путь: rollback, затем закрытие с подавлением ошибки close.

- Альтернатива: отдельный тип результата или исключения «зафиксировано, но close не удался» — отвергнута: у `inTransaction` пока нет продакшн-вызывателей, которым нужно различие; журнал достаточен, а тип можно добавить позже без смены семантики успеха.
- Альтернатива: повторная попытка close — отвергнута: соединения одноразовые (per-transaction), драйвер освобождает нативные ресурсы при сборке; повтор не добавляет гарантий.
- Сбой и commit, и close: приоритет у ошибки commit; ошибка close — подавленная (паттерн уже есть в `rollbackQuietly`).

### D3. Откат миграции: очистка staging и best-effort checkpoint

**3a. Очистка.** В начале `migrateWithBackup` (до создания копии) удаляются файлы `<имя-БД>.*.restore` в каталоге БД, оставшиеся от краха процесса в прошлый раз. Безопасно: второй экземпляр приложения исключён `InstanceLock`, имя матчится по префиксу и суффиксу каталога БД.

**3b. Checkpoint как best-effort.** Сбой `checkpoint` при откате больше не прерывает восстановление: пишется предупреждение в журнал, затем выполняются `deleteSidecars` и атомарная замена файла копией. Потеря зафиксированных после копии транзакций частично применённой миграции допустима: копия консистентна и до-миграционная, повторный запуск миграции применит их заново; текущее поведение («восстанавливайте вручную» при живой проверенной копии) хуже.

- Альтернатива: сохранить прерывание отката при сбое checkpoint — отвергнута по причине выше.
- Альтернатива: при сбое checkpoint не удалять sidecars и не делать replace — отвергнута: основной файл остаётся повреждённым/полумигрированным без пути восстановления.
- Сбой замены: прежнее поведение — временный файл удаляется, ошибка несёт путь к копии для ручного восстановления.
- Откат изменения: кодовый, формат файлов не меняется.
- Платформы: `createTempFile`/`ATOMIC_MOVE` в пределах одного каталога — атомарность на всех трёх ОС; `newDirectoryStream` для очистки — везде; если staging-файл занят другим процессом (Windows), удаление пропускается с записью в журнал и не мешает миграции.

### D4. Соединения Flyway: внешние ключи и полная синхронизация

`existingFileProperties()` дополняется `SQLiteConfig.enforceForeignKeys(true)` и `setSynchronous(FULL)`. Режим журнала эти соединения по-прежнему не задают. Расширение действует на все служебные соединения (Flyway, `integrity_check`, `VACUUM INTO`, checkpoint): для читающих проверок прагма FK безвредна, для `VACUUM INTO` полная синхронизация усиливает durability копии.

- Альтернатива: отдельный метод `flywayProperties` только для Flyway — отвергнут: отличие в две строки, а дублирование конфигурации проще рассинхронизировать, чем обобщить.
- Альтернатива: задать ещё и WAL — отвергнута: служебные соединения сознательно не меняют режим журнала файла (комментарий SqliteSupport.java:88–90).
- Сбой: прагмы per-connection, на файл не влияют; при отказе прагмы соединение не открывается — обычный путь ошибки Flyway.

## Risks / Trade-offs

- [Окно настроек нельзя закрыть при зависшей навсегда записи] → запись идёт на локальном диске в пользовательский каталог, вечное зависание маловероятно; крайний путь — завершение процесса (WAL/атомарная запись держат файлы консистентными). Таймаут — Non-Goal.
- [Снятие блокировки «Отмены» меняет ощущения от диалога] → кнопки остаются видимыми, но неактивными только на время записи; сценарий «Сохранение не блокирует интерфейс» спеки сохраняется.
- [Best-effort checkpoint молча теряет частично применённые миграции] → копия проверена `integrity_check`, история в ней до-миграционная; потерянное применяется повторным запуском; событие журналируется.
- [FK ON ломает существующую миграцию] → V1 содержит только DDL без нарушений FK; фиксируется тестом с миграцией-фикстурой, нарушающей внешний ключ.
- [Новые ветки в `run`/`restore` снижают покрытие мутаций] → порог из `gradle.properties`, тесты каждой ветки в задачах.

## Migration Plan

Изменение чисто кодовое: форматы файла настроек, БД и резервных копий не меняются. Развёртывание — обычная сборка; откат — revert коммитов без миграций данных.
