# Design

## Context

Мотивацию и перечень проблем см. в `proposal.md`, требования — в дельта-спецификациях.

Текущее устройство выхода:

```
requestExit()  (UI, exiting = true)
   |  состояние Opening
   v
service.shutdownAsync()  ---> runShutdown на потоке bonds2-db, ПОСЛЕ doOpen
                                  |
                  состояние стало AwaitingMigration
                                  v
                       ShutdownResult.REFUSED
   |
   v
onExitResult(REFUSED): exiting = false, warn("Идёт миграция")   <-- ложно
askAboutMigration():   exiting == true -> диалог не показан
итог: AwaitingMigration без диалога, приложение не завершено
```

Сервис по спецификации `database-lifecycle` отказывает в остановке, пока ждёт решения о миграции; это поведение остаётся. Решение о миграции принимает слой интерфейса, поэтому и отказ от миграции при выходе должен инициировать он: так уже сделано для случая, когда выход запрошен в состоянии `AwaitingMigration`.

## Goals / Non-Goals

**Goals:**
- Выход при результате «нужна миграция», пришедшем после запроса выхода, завершает приложение без диалога и без изменения файла БД.
- Перенос WAL при закрытии не создаёт файл БД ни на одной из трёх ОС.
- Очистка копий не может удалить только что созданную копию.

**Non-Goals:**
- Менять контракт `DatabaseService` и спецификацию `database-lifecycle`.
- Менять порядок остановки при настоящей миграции (`Migrating`).
- Реорганизовывать длинные требования в спецификациях (см. «вне рамок» в `proposal.md`).

## Decisions

### 1. Повтор остановки в контроллере при отказе в `AwaitingMigration`

`DatabaseController.onExitResult` при `REFUSED` смотрит на состояние сервиса (`service.state()`, оно `volatile` и не отстаёт от интерфейсного свойства):

- `AwaitingMigration`: вызывается `declineMigration()`, затем снова `shutdownAsync(SHUTDOWN_TIMEOUT)`; результат обрабатывается тем же `onExitResult`. Флаг `exiting` остаётся `true`, предупреждение не показывается.
- `Migrating`: прежнее поведение — `exiting = false`, предупреждение «Идёт миграция».

Последовательность `decline` → `shutdown` общая с веткой `requestExit()` для уже ожидающей миграции: выносится в один метод. После `declineMigration()` состояние `Closed`, поэтому повторный отказ невозможен; переход в `Migrating` в этот момент тоже невозможен, так как диалог не показывался (`exiting`) и команды `migrate()` никто не отправит.

Альтернативы:
- *Сервис сам отклоняет ожидающую миграцию при остановке.* Отвергнуто: нарушает сценарий «Остановка в ожидании решения о миграции» в `database-lifecycle` и переносит решение о миграции из интерфейса в сервис.
- *`askAboutMigration` при `exiting` сразу вызывает `declineMigration()`.* Отвергнуто как единственная мера: результат «нужна миграция» и `REFUSED` приходят в интерфейс в любом порядке, и надёжно обработать нужно именно `REFUSED`. Дублировать оба пути не нужно.
- *Оставить поведение, исправить сценарий («не завершается, показано сообщение»).* Отвергнуто пользователем: ложное сообщение и зависшее состояние.

Поведение не зависит от ОС: логика целиком в памяти процесса.

### 2. Перенос WAL без права создания файла

`SqliteSupport.checkpoint` открывает соединение с режимом `READWRITE` и снятым `CREATE` (как транзакции). Остальные служебные соединения (`integrityCheck`, `vacuumInto`, чтение схемы) не меняются: они работают с файлом, существование которого проверено выше по стеку, а поведение `VACUUM INTO` с таким режимом не проверялось.

Сбой при отсутствии файла (`SQLITE_CANTOPEN`) превращается в `PersistenceException` существующим путём в `Database.close()`; флаг `closed` выставляется в `finally`, поэтому БД считается закрытой и новые транзакции отклоняются.

Альтернативы:
- *Сбросить `CREATE` у всех служебных соединений.* Отвергнуто: шире, чем нужно, и требует отдельной проверки `VACUUM INTO`, который сам создаёт файл назначения.
- *Проверять `Files.exists` перед переносом.* Отвергнуто: состояние гонки между проверкой и открытием, флаг режима надёжнее.

Платформы: на Linux и macOS удаление или перемещение открытого файла возможно, и именно там проявляется дефект. На Windows SQLite открывает файл без `FILE_SHARE_DELETE`, поэтому удаление открытого файла обычно невозможно, пока соединение живо; но после того как все соединения закрыты, а файл удалён, поведение совпадает с Linux. Режим без `CREATE` на всех трёх ОС ведёт себя одинаково.

### 3. Защита новой копии при очистке

`BackupManager.pruneBackups` получает путь только что созданной копии. Копии файла БД упорядочиваются по прежнему правилу (метка времени, затем числовой суффикс); новая копия исключается из сортировки и всегда сохраняется, а из остальных остаются самые новые в количестве `BACKUPS_KEPT - 1`. Сумма всегда не больше трёх.

Альтернативы:
- *Сортировать по времени изменения файла.* Отвергнуто: `mtime` меняется при копировании или восстановлении копий пользователем и средствами резервного копирования, порядок по имени стабильнее и документирован.
- *Использовать монотонное время вместо локального для метки.* Отвергнуто: меняет формат имени копии, описанный в README и в спецификации.

Поведение при сбое: сбой удаления старой копии, как и раньше, пишется в лог и не прерывает миграцию.

### 4. Формулировка сценария «Неудачная миграция»

Только текст сценария: логическое совпадение вместо побайтного. Код `restore` не меняется; тест уже сравнивает файл с копией. Откат и сохранность данных не затрагиваются.

## Risks / Trade-offs

- [Предупреждение при закрытии удалённой БД говорит, что данные «остаются в журнале WAL и будут применены при следующем открытии», хотя файла уже нет] → вне рамок; зафиксировано как замечание, текст можно уточнить отдельным change.
- [Повтор остановки опирается на `service.state()`; если состояние изменится между отказом и повтором] → после `declineMigration()` сервис в `Closed`, а повторный `shutdownAsync` в этом состоянии допустим; в худшем случае приложение получит ещё один `REFUSED` и покажет предупреждение, как сейчас.
- [Новая копия сохраняется даже при «неверном» порядке меток] → число копий не превышает трёх, лишняя старая копия просто удаляется раньше.
