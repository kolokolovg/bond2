# Design

## Context

Тир 2 аудита (см. proposal.md — Why). Три сайта: per-instance блокировка `Database` (Database.java:67) невидима для статических операций (`create`/`initialize`/`migrateWithBackup`), которые могут заменить файл отката миграции под живыми соединениями; `doClose` обнуляет `database` до попытки закрытия и в ветке внутренней ошибки не пытается закрыть повторно (DatabaseService.java:315–331); `finish` присваивает `database = opened` и публикует «открыта» без защиты — `Error` подписчика (`StatePublisher.drain` пробрасывает их, StatePublisher.java:161) оставляет хендл в поле навсегда (DatabaseService.java:370–371).

## Goals / Non-Goals

**Goals:**

- Служебные операции не выполняются над файлом, которым владеет открытый экземпляр `Database`, — отказ fail-fast без касания файла.
- Ни один путь ошибки не оставляет открытое соединение БД «бесхозяйным»: либо сервис владеет им, либо оно закрыто тихо.
- Контракты владения задокументированы там, где их нарушит программист: джавадок `Database` и статических операций.

**Non-Goals:**

- Защита от нескольких процессов (уже есть `InstanceLock`) и от symlink/регистронезависимых алиасов одного файла (см. риски).
- Изменение поведения интерфейса: все новые отказы — ошибки программиста, пользователю не видны.
- Перенос владения файлом в `DatabaseService` (сервис остаётся единственным вызывателем, контракт вводится на уровне persistence-слоя).

## Decisions

### D1. Реестр открытых экземпляров в `Database` с fail-fast отказом

Статическое поле `ConcurrentHashMap<Path, Database>`: ключ — `file.toAbsolutePath().normalize()`; запись в приватном конструкторе (через него проходят все фабрики, включая тестовый с `ConnectionFactory`), снятие в `close()` под write-блокировкой (в том числе при ошибке checkpoint — экземпляр в `finally` всё равно помечен закрытым). `create`, `initialize` и `migrateWithBackup` (пакетные варианты с `locations` включительно) первым делом проверяют реестр для своего пути и бросают `PersistenceException` с сообщением вида «Файл уже открыт этим экземпляром приложения: <путь>» — тип уже обрабатывается всеми вызывателями слоя.

- Альтернатива: общий статический `ReentrantReadWriteLock` на путь — отвергнута: транзакции экземпляра держали бы read-блок и статические операции молча ждали бы (или тупик с `close`), а fail-fast явно ловит ошибку программиста.
- Альтернатива: джавадок-контракт без кода — отвергнут: не защищает от нарушения, аудит именно про это.
- Поведение при сбое: отказ реестра происходит до любых файловых операций (проверка первой строкой), файл и копии гарантированно не тронуты; сам реестр не падает (map-операции не бросают).
- Платформы: ключ — нормализованный абсолютный путь; на Windows пути регистронезависимы и разные написания одного файла дадут два ключа (риск R1); `toRealPath` не используется, потому что `create` работает с ещё не существующим файлом.

### D2. Тихая повторная попытка закрытия в `doClose` при внутренней ошибке

В ветке `catch (RuntimeException | Error e)` после журнала вызвать существующий `closeQuietly(opened)` и лишь затем `failed(...)`. Хендл обнуляется как сегодня (строка 315), но соединение получает вторую тихую попытку закрытия; успех повтора не подменяет исходную ошибку (поведение и тексты результата не меняются), сбой повтора журналируется внутри `closeQuietly`, `VirtualMachineError` пробрасывается им как положено.

- Альтернатива: оставить как есть — отвергнуто: reopen даёт второе соединение к тому же WAL-файлу, класс ошибок «занято другим процессом».
- Альтернатива: повтор с ожиданием/паузой — отвергнут: `Database.close()` идемпотентен, повтор нужен один и сразу.
- Поведение при сбое: если и повтор упал — состояние то же, что сегодня (ошибка пользователю, сервис жив), но попытка зафиксирована в журнале.

### D3. Защита публикации «открыта» от `Error` подписчика

В `finish` обернуть публикацию: `database = opened; try { publish(new DbState.Open(file)); } catch (Error e) { database = null; try { closeQuietly(opened); } catch (Error fatal) { e.addSuppressed(fatal); } throw e; }`. Порядок «сначала поле, потом публикация» сохраняется: подписчики видят «открыта» только у готового владельца. Проброшенный `Error` попадает в существующую страховку `submit` → `failed(OpenFailures.unexpected(e))` → публикация «закрыта (внутренняя ошибка)» — новых веток состояния не появляется.

- Альтернатива: поменять порядок (публикация до присвоения поля) — отвергнута: окно, когда состояние уже «открыта», а владельца нет; `doClose` в нём отверг бы закрытие.
- Альтернатива: глотать `Error` подписчика внутри публикации — отвергнута: `StatePublisher` сознательно передаёт фатальные ошибки, это контракт существующей спеки «Публикация состояния».
- Поведение при сбое: если тихое закрытие тоже упало (`fatal`), оно присоединяется подавленным к исходной ошибке, исходная пробрасывается — фатальные ошибки не поглощаются.
- Платформ: не касается.

## Risks / Trade-offs

- [R1: алиасы одного файла (symlink, регистр на Windows) обходят реестр] → вероятность низкая: приложение строит путь из настроек одним способом; фиксация в рисках вместо `toRealPath`, который несовместим с `create` по несуществующему пути. При повторении — перейти на канонизацию при существующем файле.
- [R2: реестр держит сильную ссылку на `Database`, забытый незакрытый экземпляр течёт] → то же поведение, что и сегодня (экземпляр и так удерживал бы соединение), но реестр продлевает жизнь ссылки; `close()` гарантированно снимает; тесты проверяют снятие после ошибки checkpoint.
- [R3: новые отказы сломают неизвестных вызывателей статических операций] → вызыватель в приложении один (`DatabaseService`, сериализован и не вызывает их при открытой БД); отказ — `PersistenceException`, уже обрабатываемый как «внутренняя ошибка».
- [R4: pitest-покрытие новых веток catch (Error)] → каждая ветка получает тест; порог 70% из `gradle.properties`.

## Migration Plan

Изменение чисто кодовое, форматы файлов не затрагиваются. Откат — revert коммитов. Новые отказы API не пересекаются с UI-путями приложения.
