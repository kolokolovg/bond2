# Design

## Context

Greenfield: каталог содержит только `openspec/` и `.opencode/`. В PATH нет ни `java`, ни `gradle`, поэтому JDK 21 и Gradle должны приходить через toolchain и wrapper. Мотивация — см. proposal.md.

## Goals / Non-Goals

**Goals:**
- Одна команда `./gradlew check` — все быстрые обязательные проверки.
- Тяжёлые проверки (PIT, OpenJML) — отдельные задачи, всегда запускаемые в CI.
- Минимум конфигурации: один модуль, version catalog.

**Non-Goals:**
- Бизнес-логика облигаций: приложение — минимальный носитель проверок (домен уточняется отдельным change).
- Многомодульная структура, публикация артефактов, Docker.
- Формальная верификация всего кода: только выделенный чистый модуль.

## Decisions

- **Gradle 9.x, Kotlin DSL, wrapper**: Gradle 9.x поддерживает Java 21 и новее. Альтернатива Groovy DSL отвергнута ради типобезопасности.
- **Единый JDK 21 для всего проекта** (LTS). OpenJML содержит встроенный javac 21 и не работает с другими версиями, а остальные инструменты (Error Prone, SpotBugs, PIT, JaCoCo) работают на 21 и 25. Единая версия исключает расхождение между компилируемым и верифицируемым кодом. Альтернатива «Java 25 везде, кроме `src/verified`» отвергнута: два JDK и неявное подмножество синтаксиса для верифицируемого кода.
- **Toolchain `languageVersion = 21` + foojay-resolver-convention**: JDK отсутствует локально, авто-загрузка делает сборку воспроизводимой. Альтернатива — требовать установленный JDK, хуже для onboarding.
- **Тесты: JUnit 5 + AssertJ + jqwik**: jqwik даёт property-based и работает на платформе JUnit. Альтернатива junit-quickcheck менее поддерживается.
- **Покрытие: JaCoCo** с `jacocoTestCoverageVerification` в `check` (порог по умолчанию 80% строк).
- **Мутации: gradle-pitest-plugin + pitest-junit5-plugin**, отдельная задача `pitest`, порог 70%. В `check` не входит из-за длительности.
- **Статический анализ: Error Prone + NullAway** на этапе компиляции (`-Xlint:all`; NullAway повышен до ERROR, остальные проверки Error Prone — предупреждения); **SpotBugs** в `check`. Альтернатива Checker Framework тяжелее и позже поддерживает новые JDK.
- **Стиль: Spotless** (google-java-format), `spotlessCheck` в `check`.
- **Формальная верификация: JML + OpenJML (ESC)**. Верифицируемый чистый код (например, арифметика/валидация) выносится в каталог `src/verified/java` с JML-аннотациями (дополнительный `srcDir` основного source set: код компилируется вместе с остальным и одновременно доказывается). Спецификации пишутся блочными комментариями `/*@ ... @*/`, так как google-java-format ломает строчные `//@`. Задача `openjmlProve` скачивает зафиксированную версию OpenJML в `tools/` (в `.gitignore`; в CI кэшируется) и запускает её через Exec на встроенном JDK 21 OpenJML. Чтобы доказать отсутствие переполнения `long`, домен ограничен `MAX_FACE_VALUE`; вне диапазона код-обёртка бросает `IllegalArgumentException`. Альтернативы: KeY (слишком тяжёлый), Checker Framework (не доказывает функциональные контракты).
- **Координаты и пакет**: группа `ru.onlychill`, корневой пакет `ru.onlychill.bonds2`, имя проекта `bonds2`.
- **CI: GitHub Actions**, шаги `./gradlew check pitest openjmlProve`. Допущение: хостинг — GitHub (не подтверждено).

## Risks / Trade-offs

- [Нельзя использовать возможности Java 22+, пока OpenJML не поддержит их] → осознанное ограничение; пересмотреть версию JDK при выходе OpenJML на новой Java.
- [Инструменты могут отстать при будущем переходе на новую Java] → при переходе проверять совместимость актуальных версий.
- [Мутации и OpenJML медленные] → вынесены из `check`, но обязательны в CI.
- [Авто-загрузка JDK требует сети] → кэш Gradle и каталога `tools/` в CI, документировать офлайн-вариант.
- [Пороги произвольны] → вынести в `gradle.properties` для лёгкой подстройки.
