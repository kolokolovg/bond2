# Design

## Context

`Database.open()` не держит соединения: каждая транзакция в `run` вызывает `SqliteSupport.connect` с `writeProperties` или `readProperties`. Режим открытия по умолчанию в sqlite-jdbc включает `CREATE`, поэтому отсутствующий файл создаётся пустым. Резервная копия делается так: `wal_checkpoint(TRUNCATE)`, затем `Files.copy`. Откат — удаление `-wal`/`-shm`/`-journal` и `Files.copy(..., REPLACE_EXISTING)`. Блокировка экземпляра защищает только от второго экземпляра приложения, но не от других процессов.

## Goals / Non-Goals

**Goals:**
- Транзакция никогда не создаёт файл БД.
- Копия перед миграцией согласована и не зависит от конкурирующих записей.
- Откат не оставляет частично записанный файл БД.
- Диалог миграции не появляется во время выхода.

**Non-Goals:**
- Постоянное соединение с БД.
- Изменение формата имён и числа копий.
- Прочие замечания ревью (настройки, `stop()`, `Error`).

## Decisions

**1. Режим открытия без `CREATE`.** В `SqliteSupport.properties` задаётся `SQLiteConfig.OpenMode.READWRITE` (без `CREATE`). Служебные соединения (`maintenanceProperties`) и Flyway не меняются: `create` и `initialize` сами создают пустой файл до подключения. Поведение одинаково на Linux, macOS и Windows, так как это флаг `sqlite3_open_v2`. Сбой: SQLite возвращает «unable to open database file», `run` оборачивает его в `PersistenceException("Ошибка работы с БД")`; состояние сервиса не меняется. Альтернативы: долгоживущее соединение (на Windows блокирует удаление файла, но ломает модель «соединение на транзакцию» и требует переработки блокировок); проверка `Files.exists` перед транзакцией (гонка между проверкой и подключением).

**2. Проверка `exiting`/`stopped` в `askAboutMigration`.** Если выход начат, диалог не создаётся и миграция не запускается; сервис уже получил `declineMigration`. Альтернатива: отклонять `migrate()` в сервисе — это уже происходит, но пользователь успевает увидеть диалог.

**3. Атомарный откат.** `restore` копирует резервную копию во временный файл в том же каталоге (`Files.createTempFile`), удаляет служебные файлы WAL/журнала, затем `Files.move(tmp, file, ATOMIC_MOVE, REPLACE_EXISTING)`. Временный файл в том же каталоге нужен, чтобы перемещение шло в пределах одной файловой системы. На Windows `ATOMIC_MOVE` с заменой поддерживается (`MoveFileEx`), если файл не открыт другим процессом; соединения Flyway к этому моменту закрыты. Сбой: временный файл удаляется, исключение несёт путь к копии для ручного восстановления (текущее сообщение сохраняется). Альтернатива: оставить `Files.copy` с `REPLACE_EXISTING` — при падении процесса посреди копирования файл повреждён.

**4. `VACUUM INTO` для копии.** `createBackup` выполняет `VACUUM INTO '<путь>'` на служебном соединении в autocommit; одинарные кавычки в пути удваиваются. Команда читает согласованный снимок вместе с WAL, поэтому `wal_checkpoint` перед копированием не нужен. Если целевой файл уже существует, SQLite возвращает ошибку; цикл подбора имени с суффиксом ловит именно её, определяя занятость заранее через `Files.exists` и обрабатывая гонку повторной попыткой. При сбое частично созданный файл копии удаляется, миграция не выполняется. `integrity_check` копии сохраняется. Отличие от `Files.copy`: копия компактна и не наследует режим WAL из заголовка — откат всё равно открывается обычным путём, так как режим WAL задаётся соединением. Альтернатива: backup API — недоступен в sqlite-jdbc в удобной форме.

## Risks / Trade-offs

- `VACUUM INTO` требует места на диске и времени, пропорциональных размеру БД; при нехватке места копия не создаётся, миграция не выполняется (данные целы).
- Копия после `VACUUM` может отличаться побайтно от исходника; тест отката сравнивает содержимое, а не байты.
- Версия SQLite в sqlite-jdbc должна поддерживать `VACUUM INTO` (3.27+) — проверяется тестом.
- Замена файла атомарна, но не защищена от сбоя питания без `fsync`; резервная копия остаётся как последний рубеж.
