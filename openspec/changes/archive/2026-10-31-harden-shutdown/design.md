# Design

## Context

Синхронная `DatabaseService.shutdown(Duration)` (`DatabaseService.java:150-164`) при `InterruptedException` возвращает безусловный `TIMED_OUT`, при `ExecutionException` — `STOPPED`; `runShutdown` (строки 221-250) при внутреннем сбое завершает future результатом `STOPPED`, журналирует и пробрасывает исключение на границу потока. `StatePublisher.drain` (строки 174-185) при `RuntimeException` подписчика тихо делает `cancel()`. Потребители синхронной остановки: `DatabaseController.shutdown()` (пути `MainWindowApp.stop()` и JVM-хука); меню «Выход» использует `shutdownAsync` + `deliverExitResult → exceptionallyAsync(onExitFailure)` — обработка сбоя цепочки выхода (диалог, сброс флага, повтор) уже реализована в UI. Хранение данных и файловые операции не затрагиваются: меняется только сообщение итогов и диагностика.

## Goals / Non-Goals

**Goals:**

- Итоги остановки отражают факт: прерывание/истечение срока ожидания не подменяет наступивший результат; сбой остановки не маскируется под «остановлена».
- Сбой подписчика, приводящий к отмене его подписки, наблюдаем в журнале.
- Поведение при сбое: ошибка остановки доходит до пользователя (меню-путь) или журнала (путь внешнего завершения); процесс завершается, как требует спека завершения.

**Non-Goals:**

- Переустройство `doClose` (catch `Error`) — предписано требованием «Сбой закрытия не оставляет БД без владельца».
- Изменение освобождения блокировки экземпляра при подлинном истечении срока — предписано требованием main-window «Завершение приложения во время операции с БД».
- Новое значение в enum `ShutdownResult` для сбоя.

## Decisions

### 1. Синхронная остановка выясняет факт, а не наблюдает себя

После `InterruptedException`/`TimeoutException` (флаг прерывания восстанавливается, как сегодня) проверяется `done.isDone()`: завершена — возвращается фактический итог (включая `TIMED_OUT` от `completeOnTimeout` — это тоже факт), не завершена — `TIMED_OUT` как честное «не дождался».

- Альтернатива: оставить безусловный `TIMED_OUT` (сегодняшнее «собственное наблюдение») — отвергнуто: прерывание потока не меняет факт завершения остановки, а ложный `TIMED_OUT` отправляет путь завершения по ветке «не остановлено» при живой остановке.

### 2. Сбой `runShutdown` завершает future ошибкой

`done.complete(STOPPED)` в catch заменяется на `done.completeExceptionally(e)`; проброс на границу потока сохраняется. Проброшенное исключение, как и сегодня, убивает поток жизненного цикла; `stopping` остаётся `true`, новые операции отклоняются (`RejectedExecutionException` → отклонение `STOPPED`). Гонка с `completeOnTimeout(TIMED_OUT)`: кто первый — тот итог; вторая попытка завершения — no-op, оба исхода честные.

- Альтернатива: значение `ShutdownResult.FAILED` — отвергнуто: расширяет публичный enum ради редкого случая; исключение естественно ложится в готовую UI-обработку `exceptionallyAsync`.
- Альтернатива: сохранить `STOPPED` с журналом — отвергнуто: это и есть маскирование, устраняемое изменением.

### 3. Синхронная остановка пробрасывает сбой; пути завершения — журналируют и идут дальше

`ExecutionException` → проброс причины вызывающему (не возврат `STOPPED`). Потребители: `DatabaseController.shutdown()` оборачивает вызов — `ERROR`-журнал и продолжение завершения (диалог в пути `stop()`/хука невозможен: тулкит гаснет, процесс обязан завершиться; `stopSettingsWriting` выполняется в `finally`). Меню-путь не меняется: `shutdownAsync` + `onExitFailure` уже показывает ошибку и допускает повторный «Выход» (спека «Пункт меню «Выход»»).

- Альтернатива: поглощать исключение в сервисе с журналом — отвергнуто: возвращает маскирование.
- Альтернатива: пробрасывать только `Error`, `RuntimeException` сводить к результату — отвергнуто: обе ошибки среды одинаково означают «остановка не состоялась»; разбор типов дублировал бы решение потребителя.

### 4. Сбой подписчика журналируется в точке отмены

В `drain` оба catch (`RuntimeException` и `Error` до проброса) пишут предупреждение с исключением. Журнал — `System.Logger`, как во всём пакете; для проверяемости поле делается внедряемым на уровне пакета (production — системный логгер).

- Альтернатива: вызвать `subscriber.onError` перед отменой — отвергнуто: контракт Flow этого не требует, подписчик только что бросил из колбэка, повторный вызов может бросить снова и затемнит исходную причину.

## Risks / Trade-offs

- [Повторная остановка после сбоя возвращает ту же ошибку — «обрабатывается заново» не чинит сервис] → так и задумано: после гибели потока жизненного цикла сервис неработоспособен; поведение задокументировано в спеке (сценарий «Повторная остановка после сбоя»), меню показывает ошибку повторно.
- [Гонка «срок истёк ровно в момент завершения»] → проверка `isDone` после исключения возвращает наступивший факт; оставшееся окно — честная неопределённость, покрыта тестом на обе стороны гонки.
- [`abandoned` не выставляется при exceptional-завершении] → не важно: поток мёртв и `stopping=true`, все операции отклоняются как остановленные; фиксируется тестом.
- [pitest: новые ветки результатов] → прямые тесты каждой ветки (прерывание до/после завершения, сбой `runShutdown`, повторный вызов после сбоя).
- [Окно «блокировка освобождена, а поток ещё пишет»] → остаётся только при подлинном таймауте, как предписывает main-window; устранение ложных `TIMED_OUT` (решение 1) сокращает реальные попадания в это окно.

Платформенная специфика (Linux/macOS/Windows) не вступает в игру: файловых и блокировочных изменений нет. Поведение при сбое и откат: хранение не меняется, WAL-журнал SQLite восстанавливает данные при следующем открытии, как сегодня.

## Migration Plan

Одно изменение, обычная сборка (`./gradlew check -Pheadless=true`, затем `pitest`). Внешних потребителей нет; формат хранения не меняется. Откат — revert целиком.
