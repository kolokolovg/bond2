# Proposal

## Why

Ревью кода нашло две узкие гонки, нарушающие ключевые обещания проекта: служебные соединения SQLite (копия `VACUUM INTO`, проверка целостности, инспекция схемы) открываются с флагом CREATE и потому могут молча создать пустой файл БД на месте удалённого снаружи файла — вплоть до «восстановления» пустой копии поверх настоящей БД; а остановка сервиса может «успешно» открыть БД после своего завершения, нарушая контракт потокобезопасности.

## What Changes

- Служебные соединения (`maintenanceProperties`) открывают только существующий файл: `VACUUM INTO` для копии, `PRAGMA integrity_check` для проверки копии и инспекция схемы завершаются ошибкой, если файл отсутствует, вместо создания пустого.
- Откат миграции проверяет наличие файла копии перед проверкой целостности: исчезнувшая копия даёт явную ошибку, а не «ok» по заново созданному пустому файлу.
- Операция, поставленная в очередь потока жизненного цикла до начала остановки, не выполняется после завершения остановки: вызывающий получает отклонение, а не ложный успех.
- Результат запоздавшей операции (не только открытая БД, но и «нужна миграция» и ошибка) после истечения срока остановки не публикуется.
- Повторная остановка с меньшим сроком не помечает выполняющуюся операцию покинутой преждевременно: «покинутость» определяет только исходная остановка по истечении её собственного срока.
- Замена файла БД копией при откате миграции сбрасывает копию на диск (fsync) до атомарного перемещения, а сайдкары WAL удаляются только после успешного перемещения.

Несовместимых изменений нет: публичные API сохраняются, меняется только поведение в граничных случаях.

## Capabilities

### New Capabilities

Нет.

### Modified Capabilities

- `sqlite-persistence`: новое требование о том, что служебные соединения не создают файл БД (по аналогии с существующими требованиями про транзакции и закрытие); в требовании «Резервная копия и откат при миграции» — новые сценарии об исчезновении файла БД до копии, исчезновении копии до проверки, сбросе на диск перед заменой и порядке удаления сайдкаров.
- `database-lifecycle`: в требовании «Остановка сервиса» — гарантия невыполнения операций, поставленных в очередь до остановки, после её завершения, и игнорирование любого запоздавшего результата, не только открытой БД; в требовании «Асинхронная остановка сервиса» — повторная остановка с меньшим сроком не влияет на текущую операцию.

## Impact

- Код: `persistence/SqliteSupport.java` (режим открытия служебных соединений), `persistence/BackupManager.java` (проверка наличия копии, fsync staging-файла, порядок удаления сайдкаров), `persistence/SchemaInspector.java` (инспекция без создания файла), `dbservice/DatabaseService.java` (очередь против остановки, границы `abandoned`).
- Тесты: `persistence/*` (сценарии исчезновения файлов), `dbservice/DatabaseServiceTest` (гонки постановки/остановки, запоздавшие результаты, повторная остановка).
- Зависимости и интерфейс: без изменений.
- Проверки: затронута логика БД — обязателен прогон `pitest` помимо `./gradlew check`.

## Вне рамок изменения

- UX-мелочи ревью: накопление warning-диалогов при повторном Exit, лишний error-диалог при гонке двойного клика.
- Молчаливая отмена подписки в `StatePublisher` без диагностики.
- CI-матрица платформ (сейчас только Linux).
- TOCTOU в `Database.initialize` между проверкой пустоты и миграцией.
- Усечение `(int)` таймаута ожидания свыше ~24,8 суток и мелочи настроек (симлинки, контроль-символы в путях).
