# Design

## Context

Четыре дефекта, найденные ревью (см. proposal.md — Why): служебные соединения SQLite открываются с флагом CREATE (`SqliteSupport.maintenanceProperties` не снимает его, в отличие от `properties` и `checkpointProperties`); постановка задачи в очередь и установка флага остановки не атомарны (`DatabaseService.submit` против `shutdownAsync`); после истечения срока остановки публикуются запоздавшие результаты «нужна миграция»/«ошибка» (`finish` проверяет `abandoned` только в ветке открытой БД); повторная блокирующая остановка с меньшим сроком преждевременно ставит глобальный `abandoned`; при откате миграции временный файл не сбрасывается на диск, а сайдкары WAL удаляются до перемещения.

## Goals / Non-Goals

**Goals:**

- Закрыть окна, в которых служебная операция молча создаёт пустой файл БД или копии.
- Сделать пару «постановка в очередь — остановка» атомарной: задача, не начатая к завершению остановки, отклоняется.
- Игнорировать любой запоздавший результат операции после истечения срока остановки, не только открытую БД.
- «Покинутость» операции определяется только исходной остановкой по её собственному сроку.
- Откат миграции: сброс временного файла на диск до перемещения; неудача перемещения не теряет зафиксированные транзакции основного файла.

**Non-Goals:**

- Диагностика `StatePublisher` (молчаливая отмена подписки), UX-диалоги, CI-матрица платформ, TOCTOU в `Database.initialize`, усечение таймаута — вне рамок (см. proposal.md).
- Изменение публичных API сервиса и формата хранения данных.

## Decisions

### 1. Служебные соединения — только существующий файл

`maintenanceProperties` вызывает тот же `existingFileOnly(config)`, что и `properties`/`checkpointProperties`: режим `READWRITE` без `CREATE`.

- Альтернатива: проверять `Files.exists` перед каждым вызовом — отклонена: check-then-act, окно остаётся; флаг режима закрывает гонку на самом соединении.
- Отказ при соединении: `SQLException` от драйвера маппится существующими обработчиками вызовов (`BackupManager` — в `MigrationException` с путём, `SchemaInspector.contents` — в `PersistenceException` «Не удалось прочитать схему»).
- Проверка копии перед `PRAGMA integrity_check` остаётся явной (`Files.notExists` → `MigrationException` с путём к копии): сообщение точнее, чем «ошибка SQL», а existingFileOnly служит страховкой окна после проверки.
- Легитимных создателей файла среди вызовов нет: цель `VACUUM INTO` создаётся заранее через `Files.createFile` (`reserveBackupFile`), соединение всегда открывает уже существующий источник.
- Поведение одинаково на Linux, macOS и Windows: это флаг режима открытия в драйвере, не файловая операция.

### 2. Атомарность «постановка — остановка» через общий замок

Проверка `stopping` и `executor.execute` в `submit` выполняются под `synchronized (shutdownLock)` — тем же, что и установка `stopping` с постановкой `runShutdown` в `shutdownAsync`. Исполнитель однопоточен и FIFO: взаимное исключение гарантирует, что задача либо встала в очередь раньше `runShutdown` (успеет выполниться, остановка её закроет), либо отклонена по `stopping`.

- Альтернатива: `shutdownNow()` (сбрасывает очередь) — отклонена: молча теряет уже принятые задачи, ломает сценарий «остановка во время открытия».
- Альтернатива: повторная проверка `stopping` в теле задачи — отклонена: не отличает остановленный сервис от отката остановки (REFUSED сбрасывает `stopping`), требует рассуждений о состоянии после `executor.shutdown()`.
- Замок на горячем пути неконкурентен всю жизнь процесса, кроме момента остановки; задач из потока жизненного цикла в `submit` не поступает — взаимоблокировки нет.

### 3. Единая проверка `abandoned` для всех результатов операции

В `finish` проверка `abandoned` выполняется до публикации любого результата: «нужна миграция» и «ошибка» не публикуются, полученная БД закрывается тихо, вызывающему возвращается отклонение остановленного сервиса (как в существующей ветке открытой БД).

- Альтернатива: фильтровать состояния в подписчике — отклонена: протекает знание об остановке в слой интерфейса, нарушает «результат игнорируется» на стороне сервиса.

### 4. `abandoned` ставит только исходная остановка

Блокирующая обёртка `shutdown` больше не устанавливает `abandoned` по своему таймауту: она лишь возвращает собственное наблюдение `TIMED_OUT`. Единственный постановщик — таймаут исходной `shutdownAsync` (существующий `completeOnTimeout` + `thenAccept`), повторные вызовы получают копию future и не имеют побочных эффектов.

- Альтернатива: хранить дедлайн остановки и сверять каждый результат с ним — отклонена: усложнение ради случая, полностью закрываемого одиночным постановщиком.

### 5. Прочность отката: fsync staging-копии и перенос WAL до удаления сайдкаров

Последовательность отката: копия → временный файл рядом с БД → `force(true)` по каналу временного файла → `wal_checkpoint(TRUNCATE)` основного файла (сделать его самодостаточным) → удаление сайдкаров → атомарное перемещение `ATOMIC_MOVE + REPLACE_EXISTING`.

- `force(true)` до перемещения: потеря питания сразу после замены не оставляет укороченный файл. Канал закрывается до перемещения — на Windows перемещение открытого файла ненадёжно; на POSIX `fsync` + `rename` — стандартная пара, на всех трёх платформах поведение одинаково.
- Перенос WAL до удаления сайдкаров: в момент удаления сайдкаров основной файл уже содержит все зафиксированные транзакции; неудача перемещения оставляет самодостаточный файл. Альтернатива «удалять сайдкары после перемещения» отклонена: окно между перемещением и удалением оставляет новый основной файл со старым WAL — крах там ведёт к повреждению, что хуже потери незакрытого WAL.
- Поведение при сбое: любой шаг до перемещения не меняет основной файл; после неудачного перемещения файл самодостаточен, ошибка называет путь к копии для ручного восстановления; проверенная копия не удаляется. Если основной файл удалён снаружи — `checkpoint` завершается ошибкой (existingFileOnly, решение 1), откат прерывается с путём к копии: файл уже потерян внешне, копия сохранена.
- Занятость WAL при `checkpoint` исключена конструктивно: откат выполняется на единственном потоке жизненного цикла при закрытой БД, но ошибка «WAL занят» всё равно обрабатывается как обычный сбой отката.

## Risks / Trade-offs

- [Замок в `submit` на каждом вызове] → Неконкурентный `synchronized` дёшев; контентия только в момент остановки, когда новых вызовов уже нет.
- [Непубликация запоздавшей ошибки оставляет последнее состояние подписчика без финального «закрыта»] → `runShutdown` закрывает паблишер (`onComplete`), подписчик завершается корректно; UI и так уничтожается при остановке.
- [`force(true)` добавляет ввод-вывод в откат] → Один сброс на редкий путь отката; не влияет на транзакции.
- [Ложные срабатывания existingFileOnly при сетевых ФС, где файл «мигает»] → Ошибка явная и читаемая, повтор операции её исправляет; молчаливое создание пустой БД хуже.

## Migration Plan

Изменение только кода, формат данных и настройки не затрагиваются: откат — реверс коммита. Новые тесты добавляются вместе с фиксами; поведения сужаются только в граничных случаях (ошибки вместо молчаливых пустых файлов, отклонение вместо ложного успеха), совместимость API сохраняется.
