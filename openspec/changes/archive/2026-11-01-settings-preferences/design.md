# Design

## Context

Сейчас `SettingsStore` (273 строки) читает и пишет `settings.properties`: временный
файл, сброс на диск, атомарное переименование, срезание BOM, восстановление с
`.bad`-копиями, выметание орфанов. Запись асинхронна: `SettingsPersistence` держит
выделенный поток, окно настроек блокируется на время записи, цепочка выхода ожидает
запись до 5 секунд (ca4eed1). Мотивация замены — в proposal.md; состав хранимого не
меняется: два ключа `database.path` и `database.autoOpen`, модель `Settings` и валидация
пути `SettingsValidator` остаются как есть.

## Goals / Non-Goals

**Goals:**

- Хранение двух значений без файловой машины: класс проблем (повреждение файла,
  атомарная замена, BOM, временные файлы, ожидание асинхронной записи) удаляется, а не
  чинится.
- Синхронное сохранение из окна настроек без состояния «идёт запись».
- Хранилище тестируется без реестра и глобального состояния JVM.

**Non-Goals:**

- Миграция значений из `settings.properties` и любые действия с самим старым файлом.
- Изменение цепочки выхода для БД: выделенный поток выхода и закрытие БД остаются;
  исчезает только ожидание записи настроек.
- Настройки за пределами двух существующих ключей.

## Decisions

### 1. Узел `Preferences.userNodeForPackage(Settings.class)`

Узел привязан к пакету настроек; ключи `database.path` и `database.autoOpen` не
меняются. Альтернатива — `userRoot().node("ru/onlychill/bonds2")`: то же самое
явным путём; отклонена как менее идиоматичная без преимуществ. Файловое хранение как
альтернатива рассмотрено и отклонено в proposal.md — оно и есть удаляемая сложность.

### 2. Синхронная запись `put` + `flush` в потоке интерфейса

Реестр на Windows и XML на macOS/Linux пишутся за миллисекунды: выделенный поток,
`CompletableFuture saved`, блокировка окна и ожидание в цепочке выхода не нужны.

Альтернативы:

- *Сохранить асинхронную запись с одним executor* — сохраняет машину состояний окна и
  ожидание выхода, то есть ту сложность, которую изменение удаляет. Отклонена.
- *Только `put` без `flush`* — на Linux значения пишутся на диск лениво и теряются при
  аварийном завершении JVM. Отклонена: `flush` стоит миллисекунды и делает запись
  завершённой к моменту закрытия окна.

### 3. Шов для тестов — интерфейс, а не `PreferencesFactory`

`java.util.prefs.Preferences` — глобальное JVM-состояние: фабрика кэшируется статически
при первом обращении, подменить её per-тест в общем тестовом JVM нельзя. Поэтому
хранилище настроек работает через минимальный шов `SettingsBackend` (`get` / `put` /
`flush`): продакшн-реализация оборачивает `Preferences`, тесты используют in-memory
реализацию на `Map`. Альтернатива — направлять тесты в изолированный корень через
системное свойство фабрики — отклонена: глобальное состояние, порядок тестов влияет на
результат, невозможна параллельность.

### 4. Обработка сбоев

- Чтение: `BackingStoreException` или значение, не разбираемое как путь/флаг, —
  значение по умолчанию для ключа и запись WARNING в журнал; запуск не прерывается
  (прежнее правило поведения при нечитаемых настройках).
- Запись: `BackingStoreException` оборачивается в `UncheckedIOException` с сообщением
  «Не удалось сохранить настройки» — форма ошибки для окна настроек сохраняется
  (сценарий «Ошибка записи»). Тонкость: `put` меняет узел в памяти до `flush`, поэтому
  при сбое `flush` в текущей сессии может действовать новое значение, а после
  перезапуска — прежнее; сценарий «Ошибка записи» описывает именно это.

### 5. Поведение по платформам

| Платформа | Хранилище | Замечания |
|-----------|-----------|-----------|
| Windows | реестр (`HKCU\Software\JavaSoft\Prefs`) | запись и целостность — забота ОС |
| macOS | XML в домашнем каталоге (`FileSystemPreferences`) | `flush` с блокировкой файла |
| Linux | XML в `~/.java/.userprefs` | то же; худший случай — значение не сохранилось, применяется дефолт |

Худший деградационный сценарий на любой платформе — потеря одного из двух значений с
откатом к дефолту. Это не данные пользователя: БД и её файлы изменение не касается.

### 6. Сценарии, снятые вместе с поведением

MODIFIED не имеет права выбрасывать сценарии, а одноимённая пара REMOVED + ADDED
запрещена валидатором. Поэтому требования, у которых вместе с поведением умирают
сценарии, сняты и добавлены заново под новыми точными именами — так финальная спека не
тащит сценарии-зомби:

- «Окно настроек» → «Редактирование настроек»: «Отмена во время записи» и «Повторное
  сохранение во время записи» описывают состояние «идёт запись», которого больше нет;
  имя сценария «Сохранение не блокирует интерфейс» сохранено, содержание переписано
  под синхронную запись.
- «Сохранение настроек» → «Хранение настроек»: «Повреждённый файл настроек» и «Файл с
  меткой порядка байтов» заменены сценариями «Отсутствующее значение» и
  «Некорректное значение» — понятия файла больше нет.

## Risks / Trade-offs

- [Длительный или неудачный `flush` на Linux (блокировка XML)] → миллисекунды в
  норме; при сбое — сценарий «Ошибка записи» и прежние значения после перезапуска.
- [Реестр недоступен на Windows (политики, терминальный сервер)] → `BackingStoreException`
  → ошибка записи в диалоге; то же, что сегодня при недоступном файле настроек.
- [Удаление ~700 строк тестов меняет долю покрытия] → порог из `gradle.properties`
  проверяется задачей прогонов; удаляемый прод-код перекрывает удаляемые тесты.
- [Ручная правка настроек больше не файловая] → реестр и XML правятся штатными
  средствами платформы; поддержка ручного редактирования не является требованием.

## Migration Plan

Одноразовая замена в рамках разработки. Откат — реверт изменения: старый
`settings.properties` не удаляется и не читается, файловое поведение восстанавливается
без потерь.
