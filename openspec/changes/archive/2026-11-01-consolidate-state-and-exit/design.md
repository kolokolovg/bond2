# Design

## Context

Решения о жизненном цикле БД и выходе размазаны: `DbState.allows*` (меню) в `DbState`,
`mustNotStop` в `DatabaseService`, четыре `instanceof` в `DatabaseController`; фазы выхода
закодированы пятью флагами в трёх классах; машина выхода (таймауты, retry, порядок) лежит в
`ui.DatabaseController` вне мутационного гейта. Мотивация и находки — в proposal.md.
Ключевой факт о тестах: `DatabaseControllerTest` (55 тестов) выполняется через `UiQueue` без
FX-тулкита, а `DatabaseController` импортирует из JavaFX только `beans.property` — выносимая
логика FX не является по существу.

## Goals / Non-Goals

**Goals:**

- Одно место, отвечающее на «что можно в состоянии X» — `DbState`.
- Одна фаза выхода с одним владельцем вместо пяти флагов.
- Машина выхода — класс без JavaFX-зависимостей в пакете `app`, под мутационным гейтом.
- Закрыты «зомби»-сценарий и прилипший `abandoned` (два поведенческих фикса из дельт).

**Non-Goals:**

- Не меняем таймауты (30с/5с/30с), тексты диалогов, пользовательские сценарии выхода.
- Не трогаем `StatePublisher`, `OPEN_INSTANCES`, `busy` (см. proposal «Вне рамок»).
- Не перепроектируем подписку на состояние: `StateSubscriber` остаётся.

## Decisions

### 1. Предикаты остановки переезжают в `DbState`

Рядом с `allows*` добавляются `allowsShutdown()` (ложен только для `Migrating` и
`AwaitingMigration`) и `awaitsUserDecision()` (истинен только для `AwaitingMigration`).
`DatabaseService.mustNotStop` удаляется, сервис и контроллер читают предикаты.

Альтернатива — таблица решений в контроллере: отвергнута, оставляет знание расщеплённым
между слоями; альтернатива «библиотека конечных автоматов» — отвергнута как непропорциональная
пяти состояниям.

### 2. `ShutdownResult.REFUSED` получает типизированную причину

`ShutdownResult` из enum превращается в sealed-интерфейс: `STOPPED`, `TIMED_OUT` (константы) и
`REFUSED(ShutdownRefusal cause)`, где `ShutdownRefusal` — enum `MIGRATING` /
`DECISION_PENDING`. Сервис заполняет причину при отказе; контроллер вместо `instanceof` по
`service.state()` переключается по причине отказа. Новое состояние автомата, попав в
`allowsShutdown()`, автоматически попадает и в отказ остановки — против девяти ручных правок.

Альтернатива — метод `lastRefusalCause()` на сервисе: отвергнута, состояние с гонкой между
результатом и причиной; альтернатива «оставить строки-причины»: отвергнута — это уже случилось
с `OpenResult.Failed` (находка №5 средней лиги), повторять не будем.

### 3. Фаза выхода — один enum с одним владельцем

`ExitPhase { RUNNING, EXITING, CONCLUDED }` живёт в новом пакете `app`, владелец —
координатор выхода. Замены: `exiting` → `phase == EXITING`, `stopped` → `phase ==
CONCLUDED` (поздние результаты игнорируются), `exitStarted` в `MainWindowApp` — переход
`RUNNING → EXITING` через `compareAndSet` в координаторе. `MigrationFlow` получает один
`Predicate`-взгляд «выход начат или завершается» вместо пары `BooleanSupplier`.

Разрешение «зомби»: фаза `CONCLUDED` необратима для текущей попытки; сбой показа
предупреждения после `CONCLUDED` журналируется, и выход продолжается — сервис к этому моменту
уже дал итог, «оживлять» окно с замолчавшими результатами хуже, чем завершиться. Если и сам
повторный выход падает, фаза откатывается в `RUNNING` с показом ошибки — приложение не может
стать незакрываемым.

Альтернатива — полный откат `CONCLUDED → RUNNING` при любом сбое после итога: отвергнута, оставляет
приложение живым при остановленном/исчерпавшем срок сервисе — обратный «зомби».

### 4. Пакет `app` и состав координатора

Новый пакет `ru.onlychill.bonds2.app`: `ExitCoordinator` (последовательность «остановка БД →
освобождение блокировки → снятие хука», выбор таймаутов, retry после отказа с
`DECISION_PENDING`, фаза) и `ExitPhase`. JavaFX не импортируется вовсе: диалоги и выход
передаются интерфейсами (`warnBeforeExit` как `Supplier<CompletableFuture<Void>>`-порт,
`exit` как `Runnable`), по образцу существующих `Dialogs`/`Executor`-портов.

`DatabaseController` остаётся FX-адаптером: меню, диалоги, свойства состояния; `MainWindowApp`
— сборка окна и запуск потока `bonds2-exit`, вызывающий координатор. `Main` не меняется.

Альтернативы размещения: пакет `dbservice` — отвергнут, координатор управляет завершением
приложения (блокировка, хук), а не сервисом, и `dbservice` уже самый тяжёлый; сузить
исключение pitest до конкретных классов `ui` — отвергнуто, исключение по именам классов
хрупче пакетного и тихо ломается при переименованиях.

### 5. `abandoned` сбрасывается отказом остановки

«Покинутость» становится свойством попытки остановки, а не сервиса: если после истечения срока
попытка завершается `REFUSED` (сервис жив), `abandoned` сбрасывается вместе с `stopping` —
сервис полностью работоспособен (сценарий дельты `database-lifecycle`). Единственный
постановщик остаётся таймаут исходной `shutdownAsync`.

### 6. Потоки

Переходы фазы выполняются в потоке интерфейса и в цепочках завершения; читают фазу поток
жизнака `bonds2-db` (поздние результаты) и поток выхода — фаза хранится как
`AtomicReference<ExitPhase>`, видимость документируется в Javadoc. Остальная потоковая модель
не меняется.

### 7. Сбой самой остановки не оживляет сервис (обнаружено реализацией)

`closeQuietly` прощает сбои закрытия (остановка обязана завершиться), а исключение из
`runShutdown` оставляет `shutdownFuture`/`stopping` выставленными навсегда — сервис одноразов
после сбоя остановки (документированный инвариант `shutdownAsync`). Поэтому сценарий «Сбой
цепочки выхода» переписан в дельте честно: повторный «Выход» пробует цепочку снова, но при
повреждённом сервисе сообщает ту же ошибку. Оставлять старую формулировку «начинает выход
заново» означало бы обещание, которое сервис не держит; чинить одноразовость — отдельная тема
(семейство «несбрасываемые флаги», см. аудит). Решение пользователя от 2026-11-01: признать
семантику в спеке.

## Risks / Trade-offs

- [Объём миграции тестов: из ~2800 строк двух тест-классов часть переезжает в `app`] → стадии
  ниже идут в порядке «поведение сохраняется → проверяем каждой стадией»; перенос тестов
  совмещается с выносом, а не отдельной волной.
- [Sealed `ShutdownResult` меняет API — правки во всех `switch` и тестах] → компилятор
  перечисляет все места; exhaustive-`switch` превращает правку из «найти девять instanceof» в
  «исправить, куда указал компилятор».
- [Порог pitest после переноса: убийцы должны жить вне `ui`] → тесты координатора пишутся в
  `app` (excludedTestClasses покрывает только `ui`), `./gradlew pitest` — критерий готовности
  стадии 4; порог мутаций не снижается.
- [Гонки вокруг фазы: два потока пишут] → единственный писатель на переход (FX — начало,
  цепочка — итог), `compareAndSet` на старте; тест сценария «повторный выход» остаётся.

## Поведение при сбое и откат

Пути ошибок не сужаются: сбой остановки по-прежнему показывает ошибку и возвращает `RUNNING`
(сценарий «Сбой цепочки выхода»); новый случай — сбой после `CONCLUDED` — журналируется и
завершает выход. Откат изменения — реверт: пользовательских форматов и данных изменение не
касается.

## Стадии (каждая оставляет сборку зелёной)

1. Предикаты в `DbState`, сервис на них (поведение то же).
2. Sealed `ShutdownResult` с причиной; контроллер на переключении по причине.
3. Сброс `abandoned` при отказе (+ тест гонки из находки №3 охоты).
4. `ExitPhase` в `app`, замена трёх флагов, зомби-фикс, вынос координатора, перенос его
   тестов, `pitest` зелёный.
