# Design

## Context

Java 21, Gradle Kotlin DSL, JavaFX GUI (`Main` → `MainWindowApp`), без модульного `module-info`. Строгие проверки: Error Prone + NullAway (ошибка), SpotBugs, Spotless, JaCoCo (порог 0.80), PIT (порог 70%). Персистентности в проекте нет; доменных сущностей, кроме `Coupon`, нет. По решению пользователя — JDBC без ORM, Flyway для миграций, только инфраструктура.

## Goals / Non-Goals

**Goals:**
- Атомарные транзакции и корректность при параллельном доступе.
- Автоматические миграции при старте.
- Покрытие тестами, включая параллельные сценарии.

**Non-Goals:**
- Доменные таблицы и репозитории, ORM, пул соединений общего назначения, шифрование БД, сетевой доступ.

## Decisions

- **sqlite-jdbc (org.xerial) + flyway-core** без ORM. Flyway для SQLite входит в `flyway-core` (в новых версиях может потребоваться модуль `flyway-database-sqlite` — уточнить при реализации под выбранную версию).
- **WAL-режим** (`PRAGMA journal_mode=WAL`): читатели не блокируют писателя и наоборот; один писатель одновременно. Альтернатива — rollback-журнал по умолчанию: читатели блокируют запись, хуже для GUI.
- **`busy_timeout` (например, 5000 мс) и `foreign_keys=ON`** на каждом соединении; `synchronous=NORMAL` допустим с WAL.
- **Соединение на единицу работы** + небольшой собственный `DataSource`-фасад (открывает соединение с нужными PRAGMA). Общий пул не вводим (YAGNI).
- **Транзакции `BEGIN IMMEDIATE`** для записывающих единиц работы: блокировка записи берётся сразу, что исключает взаимоблокировки при апгрейде read→write и ошибки `SQLITE_BUSY` посреди транзакции. Чисто читающие — обычные (deferred) транзакции со снимком WAL.
- **API `Database.inTransaction(Work<T>)`** (функциональный интерфейс с `Connection`): commit при успехе, rollback при любом `Throwable`, закрытие соединения в `finally`. Проверенные SQL-ошибки оборачиваются в непроверяемое `PersistenceException`.
- **Расположение файла**: путь передаётся конструктору (для тестов — временный каталог JUnit `@TempDir`); в приложении — каталог данных пользователя (`~/.local/share/bonds2/bonds2.db` на Linux, аналоги на других ОС), каталог создаётся при необходимости.
- **Миграции** в `src/main/resources/db/migration/V1__init.sql` (минимальная служебная миграция); Flyway запускается в `Database.open(...)` до выдачи API.
- **Исключения из проверок** UI-обвязки не расширяются: новый код покрывается тестами в штатном порядке, включая многопоточный тест (`ExecutorService` + `CountDownLatch`) на потерянные обновления и тест отката.

## Risks / Trade-offs

- [`SQLITE_BUSY` при долгой записи] → `busy_timeout` + `BEGIN IMMEDIATE` + короткие транзакции; тест на таймаут.
- [Один писатель ограничивает пропускную способность записи] → приемлемо для настольного приложения.
- [Вызов БД из FX-потока подвесит UI] → API синхронный; вызывающий отвечает за вынос в фон (отдельная задача при появлении доменных сценариев).
- [Native-библиотека sqlite-jdbc на разных ОС и SpotBugs-шум от Flyway/JDBC] → sqlite-jdbc содержит нативные библиотеки в jar; ложные срабатывания подавлять точечно.
- [Совместимость версий Flyway и SQLite] → зафиксировать версии в каталоге версий и проверить тестом миграции.
