# Proposal

## Why

Весь composition root живёт в `MainWindowApp.start()`: приложение существует только через
жизненный цикл JavaFX `Application`, ядро нельзя запустить без UI-тулкита, а действие внешней
остановки и хук завершения JVM размещены в static-поле UI-класса вне мутационного гейта
(известный остаток внешней цепочки из аудита). Изменение — второй шаг плана реорганизации
после завершённого `db-file-lifecycle`: перенос композиции в ядро `app/`.

## What Changes

- Новый composition root `AppCore` в `app/`: инверсия входа — ядро стартует UI, а не UI
  собирает ядро. Тулкит поднимается через `Platform.startup` за портом (пакет `app/`
  остаётся без JavaFX, как требует `NoJavaFxDependencyTest`); класс `MainWindowApp`
  (наследник `Application`) удаляется, из `Application` больше ничего не используется.
- Стартовый конвейер ядра: подъём тулкита → блокировка единственного экземпляра → сборка
  ядра (презентер с координатором выхода, регистрация хука JVM) → главное окно → открытие
  единственной БД → фиксация готовности (READY). Отказ шага до окна — сообщение и завершение
  процесса.
- Хук завершения JVM и действие внешней остановки переезжают из static-поля
  `MainWindowApp` в ядро; код попадает под pitest, закрывая пункт аудита о мутационном
  остатке внешней цепочки.
- Цепочку штатного завершения (остановка БД → освобождение блокировки → снятие хука)
  запускает и дожидается ядро на выделенном потоке; триггер `Application.stop()` исчезает.
- Presenter-логика `DatabaseController` (busy-гейтинг, маршрутизация результатов открытия
  и копирования) переносится в `app/` под pitest; в `ui/` остаётся тонкий FX-адаптер
  (свойства, диалоги).
- `Main` сводится к запуску ядра.

Видимое пользователю поведение не меняется; несовместимость — только внутренняя
(удаляется `MainWindowApp`, меняется проводка сборки приложения) — как **BREAKING**
не маркируется.

## Capabilities

### New Capabilities

- `app-lifecycle`: жизненный цикл приложения как целого — стартовый конвейер ядра
  (тулкит → блокировка → окно → БД → READY) с поведением при отказах шагов, завершение
  процесса после цепочки остановки и лучшая попытка остановки при внешнем завершении
  процесса (хук JVM).

### Modified Capabilities

- `main-window`: требования «Запуск второго экземпляра» и «Закрытие БД при внешнем
  завершении» переносятся из `main-window` (второе — в новую `app-lifecycle`, первое
  покрывается существующей `single-instance` и `app-lifecycle`); остальное поведение окна
  не меняется.

## Impact

- Код: `Main` (сведение к запуску ядра), `ui/MainWindowApp` (удаление, композиция
  переезжает в `app/AppCore`), `ui/DatabaseController` (худеет до FX-адаптера), новые
  классы `app/` (ядро, порт загрузки UI, презентер). `dbservice`/`persistence` не
  меняются.
- Сборка: `build.gradle.kts` — exclusions pitest не расширяются (`Main` и `ui.*`
  остаются исключёнными, `app.*` уже в цели мутаций); `application.mainClass` не меняется.
- Тесты: `MainWindowAppTest` перерабатывается (окно строит билдер, а не `Application`),
  `DatabaseControllerTest` делится между plain-JUnit-тестами презентера и FX-адаптером;
  добавляются plain JUnit-тесты конвейера с фейковым UI (без Monocle).
- Спеки: новая `app-lifecycle`; дельта `main-window` без изменения формулировок
  остающихся требований.
- Зависимости: новые не добавляются.

## Вне рамок изменения

- `database-lifecycle` не трогается: упрощение stop-семантики — отдельный кандидат.
- `MigrationFlow` и `Dialogs` остаются в `ui/`; их переезд в `app/` — отдельный кандидат.
- Слот длительных задач в цепочке остановки — лениво: конвейер и цепочка не строят
  фреймворк задач.
- Открытые хвосты прошлых аудитов (StatePublisher lost wakeup, Database OPEN_INSTANCES,
  DatabaseService abandoned, TempDir-флак) не входят.
