# Design

## Context

Тир 4 аудита (см. proposal.md — Why). Сайты: build.gradle.kts:177 (`onlyIf` по существованию каталога — залипание), 110/129/158 (`.get()` на свойствах), 121/122/137 (версии инструментов в скрипте), 102 против 126–128 (расходящиеся перечни исключений JaCoCo и pitest). Версия плагина pitest-junit5 1.2.3 ниже линии поддержки JUnit 6.1.3 (`libs.versions.toml`).

## Goals / Non-Goals

**Goals:**

- Ни одно состояние диска не может навсегда «сломать» задачу верификации: сбой загрузки лечится повторным запуском.
- Отсутствие опционального свойства сборки — не событие, а значение по умолчанию.
- Все версии инструментов — одна точка правды в каталоге версий.

**Non-Goals:**

- Изменение значений порогов покрытия и мутаций; сама политика исключений (расхождение гейтов сохраняется и объясняется).
- Подпись загрузки (GPG): релизы OpenJML не подписаны стабильно; контрольная сумма — максимум доступного доверия при явном свойстве.
- Переход на другой канал дистрибуции OpenJML (Maven Central содержит не все сборки).

## Decisions

### D1. Staging-распаковка с атомарной установкой на место

`downloadOpenjml`: архив скачивается в `build/`, распаковывается в `build/openjml-staging/`, затем каталог staging атомарно перемещается в `tools/openjml-<версия>/` (`Files.move` с `ATOMIC_MOVE`, один проект — одна файловая система). Условие выполнения меняется с существования каталога на проверку готовности инструмента: наличие исполняемого `openjml` в целевом пути. Прерванная попытка оставляет мусор только в `build/` (одноразовый каталог), целевое место не затрагивается вовсе.

- Альтернатива: маркерный файл `.complete` внутри целевого каталога — отвергнута: частичный каталог всё равно остаётся на месте и путает последующую диагностику; установка на место перемещением чище.
- Поведение при сбое: ошибка перемещения (например, целевой каталог занят) оставляет staging в `build/` — следующий запуск перезапишет его.
- Платформы: `ATOMIC_MOVE` в пределах одной файловой системы атомарен на Linux, macOS, Windows; путь staging строится от `layout.buildDirectory`, целевой — от `layout.projectDirectory`, оба локальны проекту.

### D2. Необязательная контрольная сумма архива

Свойство `openjml.sha256` (командная строка или `gradle.properties`): при наличии — SHA-256 архива считается до распаковки и сверяется; несовпадение — ошибка с обеими суммами, распаковка не начинается. Без свойства целостность обеспечивает сама распаковка: `zipTree` падает на повреждённом CRC, а staging не попадает в `tools/`.

- Альтернатива: обязательная сумма, зафиксированная в репозитории — отвергнута: источник суммы всё равно недоверенный (тот же релиз), а обязательность заставляет обновлять её руками при каждом релизе OpenJML; явное свойство даёт тот же контроль по требованию.
- Поведение при сбое: несовпадение не трогает ни `tools/`, ни staging предыдущих попыток.

### D3. Пороги — `getOrElse` со значениями по умолчанию

`coverage.minLine` → `getOrElse("0.80")`, `mutation.threshold` → `getOrElse("70")` — значения дублируют закоммиченные; `openjml.version` см. D4. Конфигурация любых задач больше не зависит от наличия пороговых свойств.

- Альтернатива: требовать свойства и падать с понятным сообщением — отвергнута: у проекта есть осмысленные значения по умолчанию, отказ — лишняя строгость.
- Альтернатива: убрать свойства вовсе — отвергнута: `-P`-переопределение порогов полезно для локальных экспериментов.

### D4. Версии инструментов — в каталоге версий

`libs.versions.toml` получает `openjml`, `pitest-tool`, `pitest-junit5-plugin`, `spotbugs-tool`. Скрипт читает `libs.versions.*`; для OpenJML сохраняется переопределение свойством: `providers.gradleProperty("openjml.version").orElse(providers.gradleProperty catalog)`. `openjml.version` уходит из `gradle.properties`; ключ кэша CI (`hashFiles('gradle.properties')`) дополняется `hashFiles('gradle/libs.versions.toml')`.

- Альтернатива: оставить в скрипте с комментарием — отвергнута: каталог версий уже точка правды для остальных инструментов (JaCoCo), захардкоженное — рассинхронизируется.
- Поведение при сбое: запись каталога отсутствует — конфигурация падает сразу и в одном месте, это фиксируемая ошибка скрипта, а не свойств окружения.

### D5. Расхождение исключений гейтов — именованные константы с политикой

Именованные `val` в скрипте: общий перечень `uiGlue` (Main, `ui.*`) и производные от него списки для pitest; исключения JaCoCo (`Main`, `MainWindowApp`) — отдельная константа с комментарием: покрытие измеряется юнит- и headless-тестами (контроллер тестируем), а мутационная фаза по `ui.*` wait-bound (комментарий уже в скрипте — переносится к константе). Расхождение становится заявленным.

- Альтернатива: выровнять перечни — отвергнута: полное исключение `ui.*` из JaCoCo ослабит гейт покрытия контроллера; включение `ui.*` в pitest сделает мутационную фазу практически непригодной по времени.

### D6. Обновление плагина pitest-junit5 до совместимого с JUnit 6

Версия переезжает в каталог (D4) и поднимается до ближайшей, поддерживающей JUnit Platform 6 (проверяется фактическим прогоном `pitest` в применении изменения). Если текущий максимум не объявляет поддержку, остаётся рабочий пин с комментарием о связке в `libs.versions.toml`.

- Альтернатива: ничего не делать (сейчас проходит) — отвергнуто: следующее обновление JUnit станет тихой поломкой в неизвестном месте.
- Риск: новая строка плагина меняет формат отчёта — проверяется прогоном и порогом.

## Risks / Trade-offs

- [R1: сумма в свойстве может устареть при смене релиза OpenJML] → свойство необязательное; устаревшая сумма падает внятно и лечится удалением свойства.
- [R2: `orElse` для версии OpenJML создаёт два источника] → иерархия зафиксирована (свойство поверх каталога), сценарий спекой; каталог — значение по умолчанию.
- [R3: обновление pitest-junit5 меняет учёт мутаций и порог] → полный прогон `pitest` в задачах; при деградации — откат версии с комментарием.
- [R4: кэш CI перестраивается после смены ключа] → разовое неудобство, кэш корректнее привязан к источнику версий.

## Migration Plan

Изменение только сборочное: продакшн-код не затрагивается, форматы данных те же. Разработчикам: `tools/` при частичном состоянии удаляется вручную один раз либо чинится повторным запуском задачи. Откат — revert; `gradle.properties` восстанавливает свойство версии.
