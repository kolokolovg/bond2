# bonds2

Приложение на Java 21 (Gradle) с встроенными тестами и инструментами верификации кода.

## Требования

Нужен любой JDK для запуска Gradle (17+; `JAVA_HOME` или `java` в `PATH`). JDK 21 для компиляции Gradle скачает сам через toolchain (foojay), если его нет локально.

## Сборка и запуск

```bash
./gradlew build                      # сборка + все обязательные проверки
./gradlew run                        # запуск: открывается главное окно (JavaFX)
```

Главное окно содержит меню «Файл»: «Сделать резервную копию…», «Повторить открытие» и «Выход», завершающее приложение. Консольного режима нет. Тесты UI по умолчанию идут на реальном дисплее; без дисплея запускайте их с `-Pheadless=true` (см. «Тесты»).

## Хранилище данных (SQLite)

Данные хранятся в единственной локальной БД SQLite (JDBC `sqlite-jdbc`) — файле `bonds2.db` в каталоге данных приложения. Путь не настраивается и не выбирается. Каталог данных по операционной системе: Linux — `$XDG_DATA_HOME` или `~/.local/share`, macOS — `~/Library/Application Support`, Windows — `%LOCALAPPDATA%` или `~/AppData/Local`; внутри него — подкаталог `bonds2`. Переменные `XDG_DATA_HOME` и `LOCALAPPDATA` учитываются, только если заданы абсолютным путём. Рядом с файлом БД лежит файл блокировки единственного экземпляра `bonds2.lock`. Если каталога данных нет, он создаётся при первом открытии БД.

Схема версионируется миграциями из `src/main/resources/db/migration/` (см. раздел «Жизненный цикл базы данных»).

Атомарность и параллельная работа: `Database.inTransaction` (запись, `BEGIN IMMEDIATE`, commit/rollback) и `Database.inReadTransaction` (чтение). Успех зафиксированной транзакции не зависит от сбоя закрытия соединения: такая ошибка записывается в журнал, а результат возвращается вызывающему, поэтому повторный вызов не дублирует зафиксированные данные. БД работает в режиме WAL с `busy_timeout` (5 с), поэтому читатели не блокируют писателя, а конкурирующие записи ждут освобождения блокировки. Миграции и служебные соединения работают с включёнными внешними ключами и полной синхронизацией, режим журнала файла при этом не меняется. Вызовы синхронные — из потока JavaFX их лучше выносить в фон.

Файл БД должен лежать на локальном диске: WAL ненадёжен на сетевых файловых системах (NFS, SMB/CIFS и подобных). Транзакции работают с `synchronous=FULL`: зафиксированная транзакция переживает потерю питания и сбой операционной системы. Приложение однопользовательское и однопроцессное: один файл БД обслуживает один экземпляр приложения.

## Жизненный цикл базы данных

### Открытие при запуске

После показа окна приложение безусловно открывает единственную БД `bonds2.db` в каталоге данных. Если файла БД нет, он создаётся автоматически с актуальной схемой, поэтому окно приложения открывается всегда. Ошибка открытия показывается сообщением, приложение продолжает работать без БД; повторить попытку можно через «Файл → Повторить открытие» (доступна, когда БД не открыта). Пока идёт открытие или миграция, остальные пункты меню (кроме «Выход») заблокированы. Строка состояния внизу окна показывает «БД открыта» или «БД не открыта» с причиной, например «схема устарела».

Чужая SQLite-база, то есть файл без истории миграций приложения, в котором есть таблицы, views, triggers, индексы, служебные таблицы `sqlite_*` либо ненулевые `application_id`/`user_version`, не открывается и не меняется: строка состояния показывает «БД не открыта: не база bonds2», миграция не предлагается. Пустой файл (0 байт) и SQLite-файл без объектов схемы инициализируются актуальной схемой без вопроса о миграции.

### Резервная копия

«Файл → Сделать резервную копию…» доступна при открытой БД. Она открывает диалог выбора места, и копия создаётся командой SQLite `VACUUM INTO` (включая данные из журнала WAL) с проверкой целостности: копия пишется во временный файл рядом с целью, проверяется, сбрасывается на диск и затем атомарно заменяет выбранный файл. При сбое временный файл удаляется, выбранный файл остаётся прежним, пользователю показывается причина (файл занят, нет места, путь недоступен). Резервная копия принадлежит пользователю: приложение не учитывает, не ограничивает и не удаляет пользовательские копии.

### Миграции

Если схема БД устарела, перед открытием приложение спрашивает разрешение на миграцию. Без согласия файл не меняется и БД не открывается. С согласием перед миграцией создаётся служебная копия `bonds2.pre-migration.db` в каталоге данных: командой `VACUUM INTO` во временный файл в том же каталоге, с проверкой целостности и атомарной заменой прежней служебной копии. Это страховка от успешной, но ошибочной миграции. Если копию создать не удалось, миграция не выполняется, файл БД не меняется.

Весь неприменённый набор миграций применяется в одной транзакции SQLite: сбой любого скрипта откатывает транзакцию целиком, и файл БД остаётся до-миграционным. Восстановления из копии внутри приложения нет.

Таблица `flyway_schema_history` — внутренняя деталь приложения: вручную её не изменяйте.

### Ручное восстановление из копии

Приложение не восстанавливает БД из копии само. Процедура:

1. Закройте приложение.
2. Замените файл `bonds2.db` в каталоге данных нужной копией — например, `bonds2.pre-migration.db` (состояние до последней миграции) или пользовательской резервной копией, созданной через меню.
3. Запустите приложение: БД откроется по общим правилам версии схемы. Если схема в копии новее версии приложения, открытие отклоняется.

### Судьба прежних файлов

Копии вида `*.bak-*` и временные файлы `*.restore` от старых версий приложения не удаляются приложением — их можно удалить вручную. БД, лежавшая вне каталога данных (старые версии позволяли выбрать путь), приложением не ищется и не переносится: после обновления приложение создаст новую пустую БД, прежний файл не тронут. Чтобы вернуть прежние данные, при закрытом приложении скопируйте старый файл в каталог данных под именем `bonds2.db`.

### Откат на старую версию приложения

Та же БД открывается старой версией приложения, пока версия схемы ей известна. Если новая версия успела применить миграции, старая версия отклонит открытие с сообщением «схема новее приложения»; вернуть состояние до миграции можно ручным восстановлением из `bonds2.pre-migration.db` (см. выше).

### Единственный экземпляр и завершение

Приложение удерживает блокировку `bonds2.lock` в каталоге данных. Второй экземпляр не открывает окно и БД: он показывает сообщение «приложение уже запущено» и завершается.

Жизненным циклом БД (открытие, миграция, резервное копирование, остановка) владеет `DatabaseService` из пакета `ru.onlychill.bonds2.dbservice`: он не зависит от JavaFX, выполняет операции строго по одной на потоке `bonds2-db` и публикует состояние через `java.util.concurrent.Flow.Publisher`. Отклонение операции (`OpenResult.Rejected` / `CloseResult.Rejected`) несёт типизированную причину `RejectionCause` отдельным значением наряду с пользовательским текстом: потребитель различает отклонения по значению причины, не разбирая текст сообщения. `DatabaseController` из пакета `ru.onlychill.bonds2.ui` — тонкий адаптер: он подписывается на состояние, переносит его в поток JavaFX, различает отклонения по причине и показывает диалоги; сценарий диалога миграции — `MigrationFlow` внутри пакета `ui`. Протокол выхода — фазы (работа / выход начат / итог известен), сроки и порядок «остановка БД → освобождение блокировки `bonds2.lock` → снятие хука завершения JVM» — выполняет `ExitCoordinator` из пакета `ru.onlychill.bonds2.app`: он не зависит от JavaFX и потому покрыт мутационными тестами наравне с логикой сервисов. Доступность действий в каждом состоянии БД определяют предикаты самого состояния (`DbState.allowsShutdown/...`), а отказ остановки несёт типизированную причину (`ShutdownResult.Refused`), поэтому новое состояние автомата не требует правок в точках разбора. Выделенный поток завершения не является демоном: поток интерфейса не блокируется, процесс живёт до конца цепочки и завершается сам с кодом 0, а блокировка освобождается строго после остановки БД.

Внешнее завершение процесса — сигнал (`SIGTERM`), конец сессии, остановка из среды разработки — закрывает БД через хук завершения JVM: он выполняет лучшую попытку остановить сервис БД с сроком 5 секунд, не касаясь интерфейса, и ничего не делает, если сервис уже остановлен штатным выходом. Немедленное уничтожение процесса (`SIGKILL`) не перехватывается ничем: данные восстанавливаются журналом WAL при следующем открытии. Причины сбоев БД различаются по коду результата SQLite: занятая другим процессом база (сообщение предлагает повторить позже), повреждение файла, отсутствие места на диске и недоступность файла показываются отдельными сообщениями.

## Тесты

| Команда | Что делает |
| --- | --- |
| `./gradlew test` | модульные (JUnit + AssertJ) и property-based (jqwik) тесты, затем отчёт JaCoCo |
| `./gradlew jacocoTestCoverageVerification` | падает, если покрытие строк ниже `coverage.minLine` (0.80) |
| `./gradlew pitest` | мутационное тестирование (PIT), порог `mutation.threshold` (70%); отчёт `build/reports/pitest/` |

Без графического дисплея (CI, SSH) добавьте `-Pheadless=true`: JavaFX работает в headless-режиме Monocle для `test` и `pitest`. Monocle входит в JDK с JavaFX (например, Liberica Full), на обычном Temurin флаг не сработает.

Пороги задаются в `gradle.properties` (значения по умолчанию 0.80 и 70 зашиты в сборочном скрипте, отсутствие свойств не роняет сборку) и переопределяются, например: `-Pcoverage.minLine=0.9`.
Отчёт покрытия: `build/reports/jacoco/test/html/index.html`. `check` включает тесты и проверку покрытия, но не `pitest` (он медленнее; запускается в CI отдельно).

## Статический анализ и стиль

Всё ниже входит в `./gradlew check`:

- **Error Prone + NullAway** — при компиляции; нарушение null-безопасности (`@Nullable` из JSpecify) — ошибка сборки. Проверяются только основные исходники (`src/main`, пакеты `ru.onlychill.bonds2`); для тестов Error Prone отключён.
- **SpotBugs** — анализ байткода (`spotbugsMain`, `spotbugsTest`), отчёты в `build/reports/spotbugs/`.
- **Spotless** (google-java-format, ktlint для `*.gradle.kts`) — `./gradlew spotlessCheck` проверяет, `./gradlew spotlessApply` исправляет.

## Формальная верификация (JML + OpenJML)

Чистая арифметика купона вынесена в `src/verified/java/ru/onlychill/bonds2/bond/CouponMath.java` и снабжена JML-контрактами (пред-/постусловия). Каталог входит в основной source set, поэтому код одновременно компилируется и доказывается.

```bash
./gradlew openjmlProve   # статическое доказательство контрактов (OpenJML ESC)
```

- Первый запуск скачивает OpenJML (~500 МБ) в `tools/` (в `.gitignore`). Версия зафиксирована в каталоге версий `gradle/libs.versions.toml` и переопределяется свойством `-Popenjml.version=…`. Архив распаковывается во временный каталог сборки и атомарно устанавливается на место: прерванная загрузка лечится повторным запуском; целостность архива можно проверить свойством `-Popenjml.sha256=<сумма>`.
- OpenJML поставляется со своим JDK 21, поэтому весь проект использует Java 21: единая версия для компиляции, тестов, анализаторов и верификации. Переход на более новую Java возможен только после выхода OpenJML с её поддержкой.
- Спецификации пишутся блочными комментариями `/*@ ... @*/`: google-java-format портит строчные `//@`.
- Нарушенный контракт приводит к ненулевому коду выхода и сообщению `The prover cannot establish an assertion (Postcondition ...)`.
- Задача не входит в `check` (долгая загрузка и работа), но обязательна в CI.

## CI

`.github/workflows/ci.yml` на каждый push и pull request выполняет `./gradlew check pitest openjmlProve -Pheadless=true` на JDK Liberica Full (с JavaFX).
